## 摘要
长周期编码智能体在不断演变的代码库状态上运行，同时越来越依赖异构能力、委托子代理和多智能体协调。这些趋势给智能体框架带来了两个互补的挑战。首先，开发者需要组合能力、重配置执行逻辑，并扩展日益复杂的智能体系统，而无需重复构建编排。其次，复杂编码任务会不断产生新证据，如语义诊断、执行结果、任务进度和上下文相关性的变化，这些证据应动态影响后续的运行时决策。我们将这些挑战概括为结构可组合性和运行时适应性。我们提出了 openJiuwen，一个专为开发者可组合性和自适应任务执行设计的开源框架。openJiuwen 提供共享的执行基座和基于 Rail 的能力组合，涵盖单智能体、委托子智能体和 Swarm Flow，使开发者能够在统一的执行语义下构建复杂的智能体框架。它进一步围绕固定模型策略调整框架控制的运行时决策，让逐步获得的证据能动态影响上下文、反馈和任务控制，从而成功完成任务。我们在 SWE-bench Verified 和 Terminal-Bench 2.1 上对 openJiuwen 进行了系统评估，分别达到 82.6% 和 87.19% 的性能，比所选官方排行榜的最强点估计分别高出 3.4 和 3.39 个百分点。这些结果表明，openJiuwen 在复杂编码任务上取得了强劲性能，同时提供了可组合且自适应的框架设计。

## Abstract
Long-horizon coding agents operate over evolving repository states while increasingly relying on heterogeneous capabilities, delegated agents, and multi-agent coordination. These trends pose two complementary challenges for the agent harness. First, developers need to compose capabilities, reconfigure execution logic, and scale increasingly complex agent systems without repeatedly rebuilding orchestration. Second, complex coding tasks continuously produce new evidence---such as semantic diagnostics, execution outcomes, task progress, and changing context relevance---that should dynamically influence subsequent runtime decisions. We characterize these challenges as Structural Composability and Runtime Adaptivity. We present openJiuwen, an open-source harness designed for both developer composability and adaptive task execution. openJiuwen provides a shared execution substrate and Rail-based capability composition across single agents, delegated sub-agents, and Swarm Flow, enabling developers to construct sophisticated agent harnesses under common execution semantics. It further adapts framework-controlled runtime decisions around a fixed model policy, allowing evolving evidence to dynamically affect context, feedback, and task control toward successful completion. We systematically evaluate openJiuwen on SWE-bench Verified and Terminal-Bench 2.1, where it achieves 82.6% and 87.19%, respectively, exceeding the strongest selected official-leaderboard point estimates by 3.4 and 3.39 percentage points. These results show that openJiuwen achieves strong performance on complex coding tasks while providing a composable and adaptive harness design.

## 2. 方法：核心思想与关键技术细节

### 2.1 总体架构

openJiuwen 围绕两个互补维度组织：
- **结构可组合性**：定义能力和智能体结构如何在共享执行基座上组合，范围从单智能体到子代理再到多智能体系统。
- **运行时适应性**：定义执行如何随着上下文、语义反馈、任务进度和可复用经验等新信息的出现而改变。

所有智能体实例（独立运行、作为子代理委托、或由 Swarm Flow 调用）都复用相同的两个基元：**内循环/外循环（Inner Loop/Outer Loop）执行引擎**与**Rail 能力接口**。

### 2.2 结构可组合性

**（1）内循环与外循环：分层执行**

- **内循环**：处理模型-工具交互。每步构造模型可见上下文 → 调用固定策略 π → 执行工具调用 → 记录观察结果 → 暴露给后续模型步骤。交互持续到模型返回答案、执行被中断或达到步数上限。生命周期回调在模型/工具边界触发，使 Rails 能观察或修改执行而不污染核心循环。
- **外循环**：一次完整的内循环调用构成一轮。每轮结束后判定是否继续或终止，处理任务级延续决策（由可组合评估器提供，如语义完成信号、资源限制、自定义条件）以及执行级控制（异常、有界重试/恢复）。外循环将基础设施故障与额外的智能体推理分离。

**（2）Rail：有序能力组合机制**

生命周期钩子空间定义为：

H = H_invoke ∪ H_call ∪ H_task

其中分别对应调用级、模型/工具调用级和任务迭代级事件。Rail 抽象表示为：

ρ = (H_ρ, f_ρ, p_ρ)

其中 H_ρ 是 Rail 附加的生命周期边界，f_ρ 是其处理器，p_ρ 是声明的优先级。在每个生命周期钩子处，附加的 Rails 按优先级执行；合并策略允许替换时，此顺序还提供能力间的受控覆盖。由此**组合顺序成为显式元数据，而非执行循环内能力分支的偶然产物**——添加/移除能力只需修改 Rail 配置，内/外循环本身保持不变。此外还引入了**能力可见性门控**：

R(u) = {ρ ∈ R | g(ρ, u) = 1}

其中 g(ρ, u) 指示 Rail ρ 是否对执行主体 u 可见。这支持有界递归委托、渐进式能力披露和角色特定能力隔离。

**（3）Swarm Flow：可组合的多智能体协调**

通过一组可组合协调算子将共享执行基座扩展到多智能体系统。核心算子包括：
- `budget()`——向下游控制逻辑暴露剩余执行预算；
- `parallel()`——并发调度多个智能体分支并同步完成；
- `compact()`——在下游处理前过滤无效/空分支结果；
- `pipeline()`——将中间结果流式传递给后续处理阶段；
- `agent_session()`——维护跨流程多阶段的有状态智能体会话；
- `human()`——自动化协调不足时引入人工干预；
- `return`——终止流程并输出最终结果。

论文以"编码智能体"为例展示组合方式：leader 查询 `budget()` 决定 worker 数量 → `parallel()` 启动多个 worker 生成独立候选 → `compact()` 去除空结果 → `pipeline()` 流式传递有效候选到审查阶段 → 有状态仲裁器（`agent_session()`）聚合候选与审查反馈 → 置信度不足时调用 `human()` → 最终 `return`。

### 2.3 运行时适应性

运行时适应性在两个时间尺度上起作用：**任务内**调整上下文构建、语义反馈以及接收/停止决策；**跨任务**将完整轨迹提炼为可复用经验。

**（1）受约束的在线运行时适应（概念框架）**

论文用约束在线优化的概念框架来刻画单任务运行时适应性。在运行时控制时期 t：

- 上下文构建：c_t = κ_t(M_t)，其中 M_t 是框架当前可用信息；
- 固定模型策略：a_t ~ π(·|c_t)，π 固定不变；
- 框架控制配置：Θ_t = (κ_t, Φ_t, ι_t)，分别控制上下文构建、语义接收与停止、诊断反馈注入；
- 轨迹级概念价值：J(Θ_0:T) = E[Σ_{t=1}^{T}(r_t − λ·cost_t)]；
- 新的证据触发状态依赖调整：Θ_{t+1} = A(Θ_t; M_t)。

适应过程需满足三个运行时可行性约束：
- **C1**：上下文不超过预算 |c_t| ≤ B_ctx；
- **C2**：诊断反馈在注入前必须可用、过滤且可接受；
- **C3**：执行必须遵从语义接受与配置的停止限制。

论文明确说明此框架用于概念说明而非数值优化算法。

**（2）上下文管理（Context Management）**

实现上下文构建组件 κ，引入：
- **渐进式压缩**：对上下文单元 m 进行 m⁰→m¹→…→mᴸ 降级（对话摘要、交互历史增量压缩、全会话压缩），近期信息保持更高保真度；
- **结构感知精简与死循环折叠**：代码 diff、日志等结构化内容先由确定性处理器精简，再使用模型摘要；重复的无生产效率推理/工具调用模式被折叠以防冗余历史消耗上下文预算；
- **卸载与检索**：大产物全量内容外置，实时上下文仅保留紧凑摘要或句柄（完整内容 → 结构化/语义摘要 → 紧凑句柄 → 按需检索），对话压缩可粗到细检索；
- **会话亲和性与 KV 缓存复用**：与推理层协调，共享会话级生命周期信息（含多智能体执行期间）。

**（3）目标模式（Goal Mode）：受接受约束的停止**

实现接受/停止组件 Φ。维护跨多次执行尝试的显式任务目标，语义评估器输出：

Φ_t(M_t) ∈ {continue, complete, blocked}

语义完成与配置的硬限制（最大尝试次数、时间或资源）分离。任务停止时刻为：

T = inf{t : Φ_t(M_t) ≠ continue ∨ g_cap(M_t) = 1}

支持三种评估模式：**自评估**（用执行中的智能体完成报告）、**独立评估**（通过单独评估路径评审轨迹）、**混合评估**（结合两者）。这些策略共享同一 Goal Mode 接口，不引入不同执行引擎。Goal Mode 与 Self-Reflection 的区别是：前者在当前任务内运作，后者在轨迹完成后作用于后续任务。

**（4）LSP 驱动的被动反馈（LSP-Driven Passive Feedback）**

实现诊断反馈注入组件 ι。Language Server Protocol 基础设施在代码变更后提供机制推导的语义证据。诊断先经排序、去重与限界：

δ_t = RankDedupLimit(Δ(s_t); K_file, K_sem)

其中 K_file 限制单文件贡献的诊断数，K_sem 限制总诊断量。可接受的反馈随后注入后续执行：

M⁺_{t+1} = M_{t+1} ∪ ι_t(δ_t)

与主动语义查询（如定义、引用查找）的区别在**控制方式**：被动诊断在相关代码变更后自动浮现，而主动语义信息由智能体显式请求。论文承认此机制范围有限——只能覆盖类型错误、符号关系、静态诊断等底层分析基础设施能暴露的属性。

**（5）自我反思（Self-Reflection）：跨任务非参数化适应**

轨迹完成后提取可复用经验：X_n = Ψ(h_{τ_n})，经验库更新为 E_{n+1} = U(E_n, X_n)（U 可实施验证、去重、合并或修订）；后续任务 τ_{n+1} 通过检索 R_{n+1} = Retrieve(E_{n+1}, q_{n+1}) 获取相关经验并纳入可用信息池 M⁺₀ = M₀ ∪ R_{n+1}。检索结果仍受上下文管理约束（可能被压缩、摘要或省略）。该机制不更新模型策略 π，构成跨任务非参数化适应。

- 修复时长分桶分析针对性地考察了长周期任务上的表现，验证了与论文主张的相关性。

**不足/偏差风险方面**：
- **无消融实验**——无法量化各运行时适应机制（如上下文管理 vs LSP 反馈 vs Goal Mode）的独立贡献，对归因有所削弱；
- **基准对比使用官方排行榜历史数据**——这些系统可能在模型、提示词、工具等方面存在差异，论文自己承认这是系统级比较而非框架单独贡献的受控估计；
- 类别层面分析中"工具覆盖面广作为解释因素"属于**推测性解释而非受控因果归因**（论文也明确承认）；
- mini-swe-agent 高推理设置在 1–4 小时桶表现低于中等设置的解释（上下文预算效应）同样被论文标记为"系统级解释而非受控因果声明"；
- >4 小时桶仅含 3 个任务，统计意义有限，论文未据此下结论。

## 6. 主要结论与发现

### 6.1 主结果

| Benchmark | openJiuwen 成绩 | 超过所选最强官方结果 | 超出幅度 |
|---|---|---|---|
| Terminal-Bench 2.1 | 87.19%（GPT-5.6 Sol） | Claude Code with Fable 5，83.8% | +3.39 个百分点 |
| SWE-bench Verified | 82.6%（Claude Opus 4.5） | 最强结果为 79.2% | +3.4 个百分点 |

### 6.2 关键发现

- **模型匹配对比中表现优异**：在 Terminal-Bench 2.1 上，openJiuwen with Fable 5 达到 84.04%，超过 Claude Code with Fable 5（83.8%）0.24 个百分点、超过 Terminus 2 with Fable 5（80.4%）3.64 个百分点。
- **类别级优势集中在工具密集型任务**：Fable 5 配置下，file operations 达 0.76（Claude Code 0.56、Terminus 2 0.52），system administration 达 0.889（Claude Code 0.778）；GPT-5.6 Sol 配置下 system administration 提升至 0.956、software engineering 达到 0.908。
- **长周期任务上保持竞争力**：SWE-bench Verified 中 openJiuwen 在 <15 分钟桶（91.75%）和 15 分钟–1 小时桶（81.23%）均获最优；1–4 小时桶达 52.38%，大幅超过同设置 mini-swe-agent（35.71%），接近 live-SWE-agent 最强结果（54.76%）。
- **线索支持上下文管理的有效性**：mini-swe-agent 高推理设置在长任务上反而低于中等设置（35.71% vs 42.86%），暗示上下文压力效应；openJiuwen 使用高推理设置却在同一桶内取得更高分（52.38%），论文将此解释为与上下文管理机制一致的证据（但非受控因果声明）。
- **跨 benchmark 一致性**：在两个差异显著的任务场景中均超过所选最强官方结果，支持 openJiuwen 作为可复用框架支撑异构长周期工作负载的设计目标。

## 7. 优点与亮点

### 方法设计层面

- **统一的执行语义**：单智能体、委托子代理与 Swarm Flow 共享同一内/外循环执行核心与 Rail 接口，避免了每种拓扑对应独立执行引擎的碎片化问题；"从单代理到多代理只改变组合方式，而非执行引擎"这一原则清晰有力。
- **组合顺序显式化**：Rail 将优先级和生命周期钩子作为显式元数据，使能力组合顺序可预测、可受控覆盖，而不依赖执行循环内的隐式分支。
- **框架控制与模型策略解耦**：运行时适应性围绕固定模型策略 π 调整框架状态（上下文、反馈、停止），避免了在长周期任务中反复调整模型策略带来的不稳定与成本问题。
- **清晰的概念形式化**：通过生命周期钩子空间 H、Rail 表示 ρ=(H_ρ, f_ρ, p_ρ)、可见性门控 R(u)、上下文构建 c_t=κ_t(M_t)、受约束在线适应框架等数学语言将系统设计精确化，便于理解和复现。
- **机制设计的系统性**：内循环管"步级推理/工具交互"，外循环管"任务级延续/恢复"，两种粒度分离合理；Context Management 管"看到什么"、LSP 被动反馈管"收到什么修正信号"、Goal Mode 管"何时
