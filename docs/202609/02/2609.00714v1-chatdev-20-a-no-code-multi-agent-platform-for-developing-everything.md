## 摘要
基于大语言模型（LLM）的多智能体系统（MAS）已展现出解决复杂任务的强大潜力，然而其开发面临一种权衡：代码框架表达力强但工程密集，而无代码构建器简化了编写过程，却将智能体交互限制在作者定义的工作流中。我们提出ChatDev 2.0：DevAll（以下简称DevAll），一个用于构建、执行和检查异构MAS的无代码平台，兼具高表达力和易用性。在表达力方面，DevAll将声明式可执行图抽象与支持循环的执行引擎相结合，使得异构智能体以及动态和循环交互能够在单一框架内被表示和执行。在易用性方面，集成的可视化界面使用户能够完全无需编写代码即可编写、运行、监控和检查MAS，包括人在回路步骤。实验表明，DevAll在三个代表性任务上以具有竞争力的性能重现了最先进的MAS，且无需针对特定任务编排代码，凸显其作为基于LLM的MAS通用平台的有效性。DevAll可在https://github.com/OpenBMB/ChatDev获取。

## Abstract
Large language model (LLM)-based multi-agent systems (MAS) have shown strong potential for solving complex tasks, yet their development forces a tradeoff: code frameworks are expressive but engineering-intensive, while no-code builders simplify authoring but constrain agent interactions to author-defined workflows. We present ChatDev 2.0: DevAll (hereafter DevAll), a no-code platform for building, executing, and inspecting heterogeneous MAS that delivers both high expressiveness and ease of use. In terms of expressiveness, DevAll pairs a declarative executable graph abstraction with a cycle-aware execution engine, so that heterogeneous agents and dynamic and cyclic interactions can be represented and executed within a single framework. For ease of use, an integrated visual interface lets users author, run, monitor, and inspect MAS, including human-in-the-loop steps, entirely without writing code. Experiments demonstrate that DevAll reproduces state-of-the-art MAS across three representative tasks at competitive performance and without task-specific orchestration code, highlighting its effectiveness as a general-purpose platform for LLM-based MAS. DevAll is available at https://github.com/OpenBMB/ChatDev.

论文的核心目标即解决这一困境：**在无代码环境中同时实现高表达力与易用性**，使用户无需编写代码即可构建、执行和检查具有动态和循环交互的异构 MAS。

## 二、论文提出的方法论

### 核心思想
DevAll 将 **多智能体系统本身**（而非静态工作流）作为可执行对象。用户通过可视化方式搭建系统，底层引擎负责编译和执行。其核心是两个关键设计：

1. **语义边（Semantic Edge）** 解耦数据流与控制流；
2. **循环感知执行引擎（CADET）** 使得包含任意循环的 MAS 图也能获得确定性调度。

### 系统架构

#### 1. MAS 编译引擎（MAS Compilation Engine）
- 将人类可读的 **YAML 规范**编译成可执行有向图 \( G = (V, E, \Theta) \)。
- `G`包含：全局配置Θ（共享内存、模型与工具注册表、工作空间、权限）；节点集V（七种内置节点类型）；边集E（语义边）。
- **语义边**被定义为一个元组 \( e = (u, v, c_e, \phi_e, \psi_e) \)，其中激活条件`c_e`决定边是否触发；**数据流策略`ϕ_e`**描述了输出如何被合并、转换、保留或清除在目标节点上下文中；**控制流策略`ψ_e`**规定了目标节点调度状态如何更新。这种设计使信息路由与执行编排可独立进行，支持超越固定工作流的语义表达。

#### 2. MAS 执行引擎（MAS Execution Engine）
- 基本原语：节点执行与语义边传播。
- 有向无环图（DAG）中，按拓扑序实现确定性逐层调度；但对于包含循环的图，拓扑序不存在，因此提出 **CADET（Cycle-Aware Dynamic Execution Topology）**算法：

**CADET 执行流程**：
1. **图压缩（Graph Condensation）**：将`G`分解为强连通分量（SCC，Strongly Connected Components），将多节点 SCC 或含自环的单个节点压缩为“凝聚节点”，形成无环凝聚图 G†（DAG），由此可计算拓扑层。
2. **循环依赖处理（Cyclic Dependency Handling）**：在 SCC 内部，CADET 将其作为带迭代范围的子图执行。通过递归识别内部边中的**回边（back edges）**与非回边，非回边在当前迭代中执行，回边则作为循环携带依赖延迟至下一轮迭代；由此 SCC 内部实际上以迭代子图方式推进。
3. **逐层调度（Layer-wise Scheduling）**：在G†上完成拓扑分层后，从与用户请求绑定的起始节点出发，按层扫描并依据运行状态触发前沿（frontier）轨迹；当遇到凝聚节点时扩展开，委托给循环依赖处理模块执行。

通过这种方式，CADET 在全局调度上恢复了确定性逐层执行（基于 DAG），同时支持任意复杂（多个、嵌套）反馈环。使用者无需编写任务特定编排代码。

#### 3. 系统界面（System Interface）
- 四个视图：**Tutorial**（示例引导）、**Authoring**（可视化图形构建）、**Execution/Launch**（运行启动与监控）、**Inspection/Laboratory**（节点级追踪、日志、token 记录、批处理实验）。
- 界面基于**元数据驱动**设计：配置面板根据编译引擎导出的节点/边处理器/记忆存储的配置元数据自动渲染，便于可扩展性。

## 六、主要结论与发现

1. **通用性**：同一个无代码平台可以在三个特征不同的领域（可视化、深度研究、软件开发）重建代表领域专门的多智能体系统，并达到与各自专用实现相当的竞争性性能，且无需任务特定编排代码。
2. **MatPlotBench 上超越专用系统**：DevAll 总体分从 CoDA 的 0.7130 提升至 0.7950，增益集中在执行通过率（0.8300→0.9900）。作者将其归因于统一运行时提供稳定的工作空间和错误处理能力。
3. **DeepResearchBench 上轻微下降**：DevAll 总体分为 0.3319 vs EDR 的 0.3500，差异在评估噪声范围内。
4. **SRDD 上表现持平**：完整性略高（+0.016），可执行性与一致性略低（-0.013/-0.0154），总体分数几乎不变。
5. **低运行开销**：在最大配置（16 个 SCC、66 节点/112 边）下，CADET 的中位数编译、规划、执行时间分别为 16.23 ms、91.96 μs、14.46 ms，相比 LLM 推理时延微不足道，且随规模近似线性增长。
6. **搭建成本可控**：复现三种工作流的估计画布操作量仅为 84–258 次。

## 七、优点

- **核心抽象创新性强**：语义边将数据流与控制流解耦，使 MAS 中可以表达任意循环而没有专门循环节点，图结构与实际执行逻辑之间建立了直接的对应关系，较之以工作流为中心的平台（依赖显式 Loop 节点）具有更清晰和自然的表达力。
- **算法设计具有理论依据**：CADET 利用图论中强连通分量的压缩，将循环 MAS 转换为 DAG 进行全局调度，同时保持了迭代级的状态，较简洁且高效地解决了任意循环的执行问题。
- **元数据驱动的无代码界面**：开发者只需注册组件配置元数据即可扩展平台，无需为每个组件单独设计界面面板，具备良好的可扩展性。
- **人机回环集成**：Human 节点会暂停执行路径来收集反馈，作为第一类节点内置，而非特殊的外挂机制。
- **评估方法合理**：选择三类输出形态差异显著的任务来证明平台通用性，标准化骨干模型以隔离工作流忠实度，具有较好的说服力。
- **开放源码**：平台已在 GitHub 开源，满足可复现性需求。

## 八、不足与局限

- **工作流设计仍需人工参与**：虽然免去了代码编写，但用户仍须将任务需求转化为图结构，并手动指定智能体角色、提示语、依赖关系和循环条件。此过程本身可能消耗较多认知精力，无代码只降低了实现门槛，并未自动化设计过程。
- **组件生态有覆盖上限**：目前的图抽象和内置组件（Agent、Human、Python、Subgraph、Literal、Passthrough、LoopCounter）可能无法覆盖所有领域特有交互模式，某些专业集成仍需定制开发扩展。
- **缺少真实用户研究**：论文未提供关于不同专业水平用户搭建效率、学习成本、易用性的实验证据，“易用性”这一核心声明缺乏经验支撑。
- **可扩展性问题未充分探讨**：对于大规模系统，可视化管理、模块化维护、多版本演进和设计经验沉淀等问题仍待解决；论文对此仅作为未来方向提及。
- **实验范围有限**：仅测评了 3 个基准（各覆盖一个参考系统），缺少广泛下游平台（如 AutoGen Studio、Langflow 等）的直接对比，也缺少对长期运行稳定性、大规模任务完成质量、多模型兼容等维度的深入研究。
- **收益量化不足**：YAML 与源代码的规模对比（表 5）虽然体现了规范精简的优势（CoDA: 7.7%、EDR: 4.4%），但对 ChatDev 1.0 比例较高（43.4%），说明收益视参考实现复杂度而异，论文未深入分析该差异的原因。
