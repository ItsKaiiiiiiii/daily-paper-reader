## 摘要
AI编程智能体正从独立工具演变为能发现并相互调用彼此专业技能的协作队友。然而，协调通道本身就可能泄露技能的知识产权。诸如MCP和A2A等协议虽然其实现在服务端运行，但仍会将每个技能的描述和类型化模式发布给所有对等方，无法隐藏技能的存在，也无法保证封装后的系统提示词不会在网络上传输。应用层隐私过滤器虽有帮助，但只能在模型决定输出敏感文本后起作用。我们采取了一种互补的协议层路径：技能即API（Skill-as-API），这是一种协调协议，其对技能的公开视图仅限于名称、描述、类型化输入/输出模式和信任层级。技能主体通过闭包捕获保留在所有者进程中，绝不跨网络传输。该协议包含四个层次，用于增加访问控制并从结构上缩小提示注入面，而非通过内容过滤。我们提供了基于XMTP的开源Python实现，其跨洲热重连延迟为1.8-2.9秒，并进行了软件工程案例研究，其中三个智能体在各自保留专有分析提示词所有权的同时，协调进行拉取请求审查。

## Abstract
AI coding agents are evolving from solitary tools into collaborative teammates that discover and invoke one another's specialized skills. But the coordination channel itself can leak a skill's intellectual property. Protocols such as MCP and A2A run implementations server-side, yet they still publish each skill's description and typed schemas to every peer, offer no way to hide a skill's existence, and cannot guarantee that a wrapped system prompt stays off the wire. Application-layer privacy filters help, but act only after the model has decided to emit sensitive text. We take a complementary, protocol-layer route: Skill-as-API, a coordination protocol whose public view of a skill is limited to its name, description, typed input/output schemas, and trust tier. The skill body is closure-captured in the owner's process and never crosses the wire. Four layers add access control and narrow the prompt-injection surface structurally rather than by filtering content. We provide an open-source Python implementation over XMTP with 1.8-2.9 s cross-continent hot-reconnect latency, and a software-engineering case study in which three agents coordinate a pull-request review while each retains ownership of its proprietary analysis prompts.

# Skill-as-API 论文总结

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **背景：** AI 编程智能体（如 SWE-agent、OpenHands）正从单机工具演变为跨组织协作的 AI 队友。在 SE 3.0（智能体软件工程）范式下，人类工程师协调大规模自主智能体，不同团队可能调用彼此封装了专有方法论的技能（如携带私有漏洞模式库的安全扫描提示词）。
- **核心痛点：** 协作通道本身就是一种泄露源。现有协议如 MCP 与 A2A，虽然实现代码在服务端不传输，但仍向所有对等方公开技能的描述和类型化模式，无法隐藏技能的存在，也无法保证封装的系统提示词不上线。
- **现有方案不足：** 应用层隐私过滤器（如 PrivacyChecker）只能在模型决定输出敏感内容后进行内容拦截，报告残留率仍约有 7–8%。
- **核心问题：** 如何在多智能体跨组织协作时，从协议结构上保护技能知识产权（代码与系统提示词），而非仅依赖事后过滤？
- **整体含义：** 提出一种互补性的协议层策略——通过限制"线上可见信息"，在智能体 ABI（应用二进制接口）层保护技能本体的机密性，而非取代加密、IAM 或内容过滤技术。

## 2. 论文提出的方法论

### 核心思想

**Skill-as-API 的核心：对技能的公共视图仅包含 `(name, d, w, v, σ_in, σ_out, t_min, h)`——名称、描述、路由提示、版本、类型化输入输出模式、最低信任层级、16 字节模式哈希。** 技能本体（代码 + 系统提示词）通过闭包捕获驻留在所有者进程内，永不进入网络通道。

### 机密性不变量

- 形式化定义：**B ∉ view(S)**——技能体（代码与系统提示）永不进入线上视图。
- 调用方式：**call(S, x) = c(filter(x, σ_in))**，其中 `filter` 丢弃不在 σ_in 中的键，调用者输入只能以具名、按模式过滤的 kwargs 到达技能。
- 系统提示词 p 在注册时被代码 c 通过闭包捕获，**不是函数参数，无法从输入路径到达**。

### 四层协议结构

1. **Layer 1：信任层级 ACL（应对 T3 信任漂移）**
   - 每个对等方有 4 个层级：UNTRUSTED(0) < KNOWN(1) < INTERNAL(2) < PRIVILEGED(3)；
   - 技能调用要求对等方层级 ≥ 技能最低信任层 t_min；
   - 入站消息类型按固定表门控（如 ping 和 trust_request 在 UNTRUSTED 即允许，discover 需 KNOWN，collab_request 需 INTERNAL，未知类型默认需 PRIVILEGED——默认拒绝）。

2. **Layer 2：自动降级（应对 T3）**
   - 引入"一次性信任"：信任不因成功使用而积累，而是**衰减**——连续 3 次失败降一级；协作 OKR 完成后降一级（下限为 KNOWN）；
   - 对等方赢得的是未来重新提升的证据，而非长期访问权。

3. **Layer 3：技能隐藏（应对 T1 技能 IP 提取）**
   - 隐藏技能与不存在的技能返回完全相同的错误字符串 "Unknown skill: X"；
   - 所有者端日志可区分，但该区分永不跨线传输，阻止调用者枚举技能命名空间发起系统性提取攻击。

4. **Layer 4：函数边界防御（应对 T2 提示词窃取注入）**
   - 两条不同属性：
     - **结构性**：p 永不跨线上，调用者输入永远不会成为系统角色参数（由 wire 格式与 kwarg 边界保证）；
     - **残差/行为性**：被调方模型仍可能在用户轮次注入时主动"复述"系统提示词——这是经典的提示词泄露向量（论文标记为 L2），不作声称已消除。

### 实现细节

- Python 3.10+ 实现，除标准库与可选 LLM SDK 外**零 Python 运行时依赖**；
- 传输层为 XMTP v3（MLS 协议）Node.js sidecar，Python 核心通过 localhost HTTP/SSE 与其通信，将加密实现排除在 Python TCB（可信计算基）之外；
- 16 字节模式哈希 h 兼作快速重连缓存键，实现 1.8–2.9 秒热重连延迟；
- 诚实披露两项复现局限：信任衰减失败计数器为内存态（重启丢重置），技能版本用精确字符串相等而非语义范围匹配。

## 3. 实验设计

### 案例研究场景

- 三个独立进程的智能体通过 XMTP 频道协调 GitHub 拉取请求（PR）审查；
- **智能体角色：** 编排者（orchestrator）+ 代码质量专员 + 安全专员，两者各自注册 t_min=1（KNOWN）的技能；编排者可发现其模式，但看不到其系统提示词。

### 验证的三类实验

1. **G1 验证（仅模式视图）：** 记录编排器侧所有 XMTP 消息，确认编排器视角只含 name、description、input_schema（diff: str）、output_schema（findings: list[str]），且与调用方系统提示词字符串（约 1,200 字符专有方法论）**零重叠**。
2. **G4 验证（注入吸收）：** 构造 10 个任务输入，覆盖 8 类 OWASP 风格注入（直接指令覆盖、角色反转、markdown/围栏逃逸、提示泄露请求、base64 编码包装、多语言改写、经由注释的间接注入、递归自调用），各前置一段代表 PR diff，发给代码质量智能体。测量（a）返回字段中是否出现逐字或改写的系统提示词；（b）结构化输出模式是否保持。
3. **G3 验证（信任衰减）：** 在同一案例运行中验证 3 次转换：升级 INTERNAL → 协作完成 OKR 后 Algorithm 1 降级回 KNOWN，以及补充验证的 PRIVILEGED → INTERNAL 过渡；确认后续 INTERNAL 级调用被拒绝。

## 6. 论文的主要结论与发现

1. **存在第四个策略性可组合的位置：** 保护可通过将泄露面从协议线上移除来达成结构性的完整覆盖。技能 IP 的保护可在协议 ABI 层实现，弥补应用层过滤的劣势。
2. **技能模式仅含白名单信息的发现机制可行：** 技能调用无需暴露系统提示词，技能体可被保留在所有者进程内，以此完成跨组织调用者能发现的模式下技能的执行。
3. **函数边界可吸收一类提示注入：** 将提示词通过闭包捕获而非待拼接参数设计，能结构性关闭"系统角色拼接"类注入向量；残余的模型行为层泄露（L2）被论文明确划出范围。
4. **短期可衰减权限足以支撑协作流程：** 信任可以通过下降来绑定单个协作周期，避免"一次协作、永久权限"问题。
5. **延迟满足跨组织协作的交互要求：** XMTP 上的 1.8–2.9 秒热重连可支持真实 SE 工作流场景。

## 7. 优点

- **问题定义清晰、精确漏洞识别：** 第一个明确呈现多智能体软件工程中协议泄露"方法论"威胁的系统化协议方法（MCP/A2A 体系未能解决的）。四个安全威胁（T1-T3）在协作场景中合理、具体，且理论范围界定清晰。

- **定义机密性不变量（B ∉ view(S)）的设计方法：** 单一不变量简化为四个相互独立、分层清晰的安全目标（G1-G5），高质量体系结构工作。它将安全设计转成一种可检查的特性。

- **有效区分结构性属性（可以确定地保证）与行为性属性（应留给过滤器）**，对可信推理与可组合防御体系结构的边界掌握得十分成熟。
