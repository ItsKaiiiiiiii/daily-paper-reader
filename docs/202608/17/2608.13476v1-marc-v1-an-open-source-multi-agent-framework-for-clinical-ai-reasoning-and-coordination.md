## 摘要
我们提出了多智能体推理与协调（MARC），一个开源框架，用确定性的多智能体编排替代单体LLM提示，用于临床推理。MARC协调角色专业化的智能体进行提取、推理、答案生成和评估，具有显式的上下文传递和可追踪的中间输出，实现分阶段失败归因。我们另外引入了一个Decomposer模块，从自然语言描述生成任务特定的智能体提示，消除了手动提示工程。框架支持基于API的和本地CPU兼容的部署，并且完全通过YAML配置，无需修改代码。MARC被设计为模型无关、可解释，并且让没有编程专业知识的临床领域专家也能使用。完整框架可在https://github.com/Penn-RAIL/MARC-v1获取。

## Abstract
We present Multi-Agent Reasoning and Coordination (MARC), an open-source framework that replaces monolithic LLM prompting with deterministic multi-agent orchestration for clinical reasoning. MARC coordinates role-specialized agents for extraction, reasoning, answer generation, and evaluation, with explicit context passing and traceable intermediate outputs, enabling stage-wise failure attribution. We additionally introduce a Decomposer module that generates task-specific agent prompts from a plain-language description, eliminating manual prompt engineering. The framework supports both API-based and local CPU-compatible deployments and is entirely configurable via YAML, without code modifications. MARC is designed to be model-agnostic, interpretable, and accessible to clinical domain experts without programming expertise. The full framework is available at https://github.com/Penn-RAIL/MARC-v1.

## 1. 核心问题与整体含义（研究动机与背景）

- 当前临床大语言模型（LLM）应用大多采用**单体提示（monolithic prompting）**策略，即用单个 LLM 实例同时完成信息抽取、推理、验证和答案生成。这种方式存在以下问题：
  - 多个认知步骤被压缩在一次模型调用中，**错误来源难以定位**——当输出错误时，无法判断是信息遗漏、推理缺陷、指令遵循失败还是格式解析问题。
  - **可解释性差**，不符合临床部署对透明性和可审计性的要求。
  - 工作流固定、依赖人工提示工程，临床专家（非程序员）难以调整或扩展。
- 放射科等临床决策通常需要整合多种信息源、进行多步推理，而现有系统往往将这一复杂过程简单化为单次生成。
- 因此论文提出 **MARC（Multi-Agent Reasoning and Coordination）** 开源框架，用**确定性多智能体编排**替代单体提示，将临床推理拆分为多个角色专用智能体的显式协作，以提升可解释性、可控性和临床可部署性。

## 2. 提出的方法论：核心思想、关键技术细节与算法流程

- **核心思想**：将临床推理流水线建模为**顺序、模块化**的多智能体系统。每个智能体负责单一认知功能，通过显式上下文传递和后继输出链式累积，形成可追踪的处理轨迹。
- **整体架构**：基于 Python 和 LangChain，支持与多种 LLM 接口对接，采用 YAML 配置文件声明智能体序列、模型分配、提示模板和知识来源（RAG），**无需修改代码**即可配置。

- **多智能体设计（默认三智能体流水线）**：
  1. **Agent 1（信息抽取）**：接收原始临床输入，提取 2–4 条任务相关证据要点（实体、发现、约束、选项等），明确不回答最终问题，保证证据收集与推理解耦。
  2. **Agent 2（分类与分析）**：同时接收原始输入和 Agent 1 的证据，执行结构化多步推理，处理歧义，并在输出末尾生成标准化判定行（如 `VERDICT = <label>` / `FINAL = yes/no/maybe`）。
  3. **Agent 3（推荐生成/答案提取）**：接收 Agent 2 的完整输出，定位判定行并原样返回其值，不添加解释或重新格式化，从而输出干净、可解析的最终答案。

- **Decomposer 模块**：
  - 作为论文的重要创新，它接收**自然语言任务描述**，调用 MedGemma 4B 在单轮对话中将任务分解为三个子任务，并自动生成角色特定的提示模板。
  - 输出结构化 JSON 规范（智能体名称、角色、完整提示），通过结构约束校验（变量绑定 `{input}`、`{previous_agent_output}`、VERDICT 格式、输出长度限制）后写入磁盘并加载到 MARC 流水线。
  - 从而**消除手动提示工程**，支持跨异构临床任务的快速流水线构建。

- **关键设计要点**：
  - 所有智能体使用 **零样本（zero-shot）、温度 = 0**，保证输出确定性和可复现性。
  - 提示模板统一包含四个部分：角色定义、任务指令、输出约束、运行时变量。
  - 显式上下文传递：Agent 1 只接收原始输入；Agent 2 接收原始输入 + Agent 1 输出；Agent 3 接收原始输入 + Agent 2 输出（其中隐式包含 Agent 1 分析）。每步中间输出均被记录，支持**阶段级错误归因**（stage-wise failure attribution）。
  - 支持条件路由（如放射学流水线中正常报告跳过分类步骤直接进入评估器）。
  
- **部署模式**：
  - **API 模式**：使用 Google Gemini 模型家族（gemini-2.0-flash、gemini-1.5-flash），仅需配置 API key。
  - **本地模式**：通过 Ollama 实现 CPU 兼容推理，适用于不允许外部 API 传输的机构环境，已有 MedGemma 4B 测试案例。
  - 两种模式共用同一份 YAML 配置，仅模型标识符不同。
  - 模型可在智能体级别任意切换，实现**模型无关性**和成本/性能/隐私的灵活折中。

## 6. 主要结论与发现

- MARC 通过确定性多智能体编排，将临床 LLM 推理从“黑盒单次生成”转变为**透明、可配置、可检查的阶段化流程**。
- 每个智能体职责单一，显式上下文传递防止信息丢失或幻觉式前文假设，中间输出日志支持**分阶段失败归因**。
- Decomposer 模块能根据自然语言任务描述自动生成提示，**显著降低人工提示工程成本**，使非程序员临床专家也能构建和调整流水线。
- 支持 API 和本地 CPU 部署，兼顾**数据隐私控制、机构部署灵活性**和模型选择的自由。
- 框架本身是模型无关、可扩展的，对未来新模型接入和复杂临床工作流的适配提供了基础。
- 作者认为，模块化、透明性和可部署性是临床 AI 安全规模化的必要方向，MARC 为此提供了一个实用框架。

## 7. 优点（方法与设计亮点）

- **可解释性优先**：角色分离 + 日志记录，让每个决策环节可审计，符合临床对透明性的硬性需求。
- **配置驱动架构**：YAML 文件定义智能体、模型和提示，实现“零代码修改”定制，降低了临床研究者的使用门槛。
- **Decomposer 自动化**：打破了手动提示工程瓶颈，支持任务自适应的流水线生成，是框架的突出创新点。
- **部署灵活**：同时支持远程 API 和本地 CPU 推理，兼顾高性能与数据隐私场景；智能体级模型切换支持成本/性能权衡。
- **确定性执行**：零样本、温度为零，保证实验结果可复现，这在临床应用中非常关键。
- **通用性强**：核心架构与具体临床任务解耦，可扩展到问答、报告生成、分类等异构任务。

## 8. 不足与局限
