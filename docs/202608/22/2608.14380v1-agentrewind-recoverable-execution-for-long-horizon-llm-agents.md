## 摘要
许多现实任务要求LLM智能体在长时间执行跨度内与环境交互。执行早期出现的错误可能会通过智能体上下文和环境状态传播，且其影响可能难以通过后续动作逆转。现有方法主要尝试通过计划细化和安全检查来减少此类错误，但在错误发生后几乎不提供支持。为了在长时程执行过程中实现恢复，我们提出了AgentRewind，一种运行时恢复框架，记录智能体上下文与受控环境的对齐检查点，使智能体能够返回较早状态并利用先前尝试的信息恢复执行。我们还构建了MettleBench，一个用于评估长时程工程任务（包含一系列相关需求）完成度和部分进度的基准。跨任务、多模型、执行策略和智能体框架的实验表明，AgentRewind在任务成功率和平均检查表进度上优于对比基线。

## Abstract
Many real-world tasks require LLM agents to interact with their environments over long execution horizons. Errors that occur early in execution may propagate through both the agent context and environment state, and their effects may be difficult to reverse through subsequent actions. Existing methods mainly seek to reduce such errors through plan refinement and safety checks but provide little support after errors occur. To enable recovery during long-horizon execution, we present AgentRewind, a runtime recovery framework that records aligned checkpoints of the agent context and controlled environment, allowing agents to return to an earlier state and resume execution with information from previous attempts. We also construct MettleBench, a benchmark for evaluating task completion and partial progress on long-horizon engineering assignments containing a series of related requirements. Experiments across tasks, multiple models, execution strategies, and agent harnesses show that AgentRewind improves task success rate and average checklist progress over the compared baselines.

## AgentRewind：面向长时程 LLM 智能体的可恢复执行——论文深度总结

### 1. 核心问题与整体含义（研究动机与背景）

- **核心问题**：长时程（Long-Horizon）任务中，LLM 智能体（agent）早期执行的一步错误，会通过**智能体上下文（context）**与**环境状态（environment state）**不断累积和传播，后续动作往往难以完全逆转其影响。例如，智能体可能过早删除关键文件、破坏配置或污染数据库状态，导致后续执行在劣化环境中进行，最终任务失败。
- **现有方法的不足**：
  - 一类方法（如 ReAct、LATS、Plan-and-Act）通过**计划细化**减少错误，但只能在执行前或执行过程中优化路径，无法应对已发生的破坏。
  - 另一类方法（如 AgentDoG、GuardAgent）通过**安全监控**拦截风险行为，但即便单步错误概率很低，累积失败风险仍会随轨迹长度上升。
  - 基于经验的方法（如 Reflexion、ExpeL）虽然能利用先前尝试的信息改进后续行为，但**缺乏错误发生后的即时恢复机制**。
- **核心含义**：作者认为，要真正提升长时程任务的可靠性，必须提供一种**运行时恢复（runtime recovery）**能力——允许智能体在发现当前路径无法推进时，将**上下文与环境状态联合回退**到较早的检查点，并携带失败经验重新执行。

### 2. 方法论：核心思想、关键技术细节与公式

#### 2.1 核心思想
- 提出 **AgentRewind**，一种位于智能体与受控外部环境之间的**运行时恢复层**。它记录对齐的检查点（agent context ↔ environment state），在错误发生后允许智能体：
  1. 选择历史检查点（checkpoint）；
  2. 将上下文与环境状态**联合还原**到该检查点；
  3. 注入**回退记忆（rewind memory）**——从失败轨迹中提取的摘要（如被证伪的假设、替代策略）；
  4. 从还原状态继续执行，产生新的轨迹后缀。

#### 2.2 形式化定义
- 标准前向执行过程可形式化为：
  - \( u_t \sim \pi(c_t) \)（LLM 根据上下文生成决策）
  - \( (s_{t+1}, o_{t+1}) = T(s_t, u_t) \)（环境状态转移与观测）
  - \( c_{t+1} = U(c_t, u_t, o_{t+1}) \)（上下文更新）
  - 轨迹：\( \tau = \{(c_0, s_0), u_0, o_1, (c_1, s_1), \dots, (c_T, s_T)\} \)
- **可恢复检查点**：在每次 LLM 决策边界记录 \( d_t = (c_t, s_t) \)，并附带描述两检查点间执行片段的元数据 \( \eta_t \)。
- **回退过程**：
  1. 智能体选择历史检查点 \( d_k \)（\( k \le T \)）；
  2. 从当前轨迹生成回退记忆 \( m \)，加入历史记忆集合 \( M \leftarrow M \cup \{m\} \)；
  3. 恢复环境状态 \( s'_k \leftarrow s_k \)；
  4. 注入记忆到上下文 \( c'_k \leftarrow \text{Inject}(c_k, M) \)；
  5. 从 \( (c'_k, s'_k) \) 继续执行，生成新轨迹 \( \tau' \)。

#### 2.3 关键技术细节
- **记录机制**：在 LLM 调用和工具调用两个钩子点透明记录轨迹（LLM 输入/输出、工具调用及结果），不改变智能体与环境的正常交互。
- **环境恢复边界**：恢复范围是**工作区目录树**（workspace），通过外部裸 git 仓库以文件级别快照实现；网络请求、外部服务调用等**不受控副作用无法撤销**，但保留前缀从执行日志恢复，不会再次触发这些副作用。
- **回退触发方式**：回退以两个工具的形式暴露给智能体——`backtrack_candidates`（列出候选回退目标）和 `backtrack_commit`（执行回退并写入记忆），由智能体自主决定何时回退。

### 3. 实验设计：数据集、基准与对比方法

#### 3.1 新基准：MettleBench
- **构成**：82 个任务，源自 5 个现有工程基准——Terminal-Bench 2.0（32.5%）、ProgramBench（26.2%）、SWE-bench（24.7%）、ProjectEval（8.8%）、GitTaskBench（7.8%）。
- **任务形式**：每个任务是一个包含**一系列有序、相互关联需求**的工程任务，形式化为 \( T = (x, s_0, U, G) \)，其中 \( G = (g_1, \dots, g_n) \) 为有序验收标准列表。
- **评估指标**：
  - 任务成功率：最终状态满足全部验收标准；
  - 平均检查表进度（checklist progress）：最长满足前缀长度占比 \( \rho(s_T) = \ell / n \)。
- **特点**：验收标准共享同一环境状态，满足一个标准可能帮助或阻碍后续标准；后续操作可能使已满足的标准失效；每个任务都有**纯前向解**，不依赖任何恢复机制。

#### 3.2 对比的方法（执行策略）
1. **Continue**：收到验证反馈后从当前状态继续执行（标准前向执行基线）；
2. **Restart with Experiences**：验证失败后重置环境到初始状态，在下一轮尝试中携带之前失败的经验文件；
3. **Safety Review**：在每次工具调用前用 AgentDoG 监控模型审查动作安全性，不安全的动作被拒绝；
4. **AgentRewind**：本文提出的可恢复执行框架。

#### 3.3 基准配置
- 默认模型：GPT-5.4；默认 harness：mini-SWE-agent。
- 终止条件（所有策略相同）：连续 5 次失败于同一验收标准时终止。
- 无步数、时间或 token 上限。

### 6. 主要结论与发现

1. **AgentRewind 在所有设置下均优于基线**：
   - GPT-5.4：成功率 87.8% vs Continue 62.2%（+25.6pp）；清单进度 94.3% vs 81.4%。
   - GPT-5.4 mini：成功率 51.2% vs 33.7%（+17.5pp）；清单进度 73.5% vs 64.6%。
2. **优势随任务难度/长度增加而扩大**：按 trace length 三分位分组后，AgentRewind 在中、长时程组别中的增益明显大于短时程组。
3. **跨基准有效**：在 Terminal-Bench 2.0 上，成功率 83.1%，优于 Continue（78.7%）和 Restart with Experiences（70.8%）。
4. **跨 harness 有效**：在 mini-SWE-agent、FnCallAgent、CodeAgent 三种框架下均实现一致提升。
5. **组件缺一不可**：去除环境回退导致最严重退化（成功率从 87.8% 降至 43.9%）；去除回退记忆也显著降低性能（降至 51.2%）；表明对齐的状态还原与经验记忆共同构成有效恢复。
6. **恢复能力本质差异**：从相同失败状态出发，AgentRewind 恢复率为 30.0%，Continue 仅 8.0%。
7. **"更长执行不保证更好结果"**：基线中 trace 长度超 300 事件的模型（如 Kimi K2.5）成功率反而最低，说明单纯延长前向执行无法解决问题。

### 7. 优点

- **问题定位精准**：指出长时程任务失败的关键在于“错误发生后缺乏恢复机制”，而非仅靠规划优化或安全拦截。
- **方法与形式化清晰**：将可恢复执行形式化为上下文-环境联合检查点 \( d_t = (c_t, s_t) \)，三个核心组件（检查点记录、联合还原、回退记忆）各有明确作用且有消融支撑。
- **基准设计有匠心**：MettleBench 的“有序、相互依赖验收标准”更贴近真实工程任务；检查表进度（最长前缀）指标有效区分不同失败程度；所有任务均确认存在纯前向参考解，公平性较好。
- **实验全面且有深度**：覆盖模型、策略、harness、基准、恢复、消融六个维度，且包含统计显著性检验。
- **评估严谨**：确定性评估器 + 人工审查 + 运行干预日志审计（仅 4 次全部为阻塞子进程清理，未影响判定）。
- **适用性广**：仅需在 LLM 调用和工具调用两个钩子点接入，即可适配不同 agent harness。

### 8. 不足与局限

- **受控环境边界有限**：只能回退工作区文件系统；网络请求、外部服务调用等副作用无法撤销（论文明确承认）。
- **依赖外部验证反馈**：当前回退触发依赖外部评估器返回“连续失败”信号，如果任务缺乏明确验证信号（如开放式任务），智能体可能无法准确判断何时该回退。
- **回退决策依赖模型自身**：是否回退、回退到哪个检查点由 LLM 自主决定，没有机制保证该决策是最优的；论文未分析回退决策的质量或失败模式。
- **算力细节缺失**：未报告推理总时延、GPU 使用量或 API 成本，难以评估框架的实际部署开销（尤其是频繁快照和恢复带来的 I/O 开销）。
- **重复性有限**：3 次重复的协议率仅 74.7%，部分配置（如 Safety Review）仅 48.8%，说明存在相当程度的运行间变异性；论文将其归因于智能体轨迹差异，但这也意味着结果可能对初始随机性敏感。
- **模型范围局限**：仅用 2 个模型（GPT-5.4 / mini）进行策略对比，未在本文最优的 Qwen3.7-Max 上验证 AgentRewind 的增益，无法完全排除模型特定交互。
- **MettleBench 人工审查粒度**：任务级审查而非逐条标准全量人工标注，虽经对抗性 LLM 复审，仍可能存在遗漏。
