## 摘要
计算机使用智能体（CUA）越来越多地以多智能体系统的形式部署，该系统将任务分解为多个子任务，并在并行虚拟机（VM）上执行。然而，一个关键的物理瓶颈是两个虚拟机的状态无法合并。先前的系统以临时方式处理这一问题，而不是将其作为一级关注点。我们提出了用于多智能体计算机使用的主干-分支协调框架，该框架将任务分解为“主干-分支”图，其中主干承载具有连续虚拟机状态的主任务流，而分支任务并行执行以收集主干完成任务所需的信息。分支虚拟机在其任务完成后即被丢弃，因此永远不会发生虚拟机合并。实验表明，在来自Odysseys的200个长时任务及三种CUA主干上，主干-分支相比基线系统将成功率提高了6.0%至16.5%，同时将每个任务的成本降低了34%至70%，这表明显式建模虚拟机状态合并约束能使多智能体计算机使用高效扩展。

## Abstract
Computer use agents (CUAs) are increasingly deployed as multi-agent systems that decompose a task into multiple subtasks executed across parallel virtual machines (VMs). However, a critical physical bottleneck is that the state of two VMs cannot be merged. Previous systems handle this ad-hoc rather than treating it as a first-class concern. We propose Spine-Branch Coordination for multi-agent computer use, a framework that decomposes a task into a "spine-branch" graph, where the spine carries the main task flow with continuous VM state and branch tasks execute in parallel to collect information the spine needs to complete the task. Branch VMs are discarded once their tasks finish, so no VM merging ever occurs. Experiments show that on 200 long-horizon tasks from Odysseys and across three CUA backbones, Spine-Branch improves success rate over the baseline system by 6.0% to 16.5%, while reducing per-task cost by 34% to 70%, indicating that explicitly modeling VM-state merging constraint enables multi-agent computer use to scale efficiently.

## 1. 核心问题与整体含义

- **研究背景**：计算机使用智能体（Computer Use Agent, CUA）通过在图形界面上执行点击、键入、滚动等操作来完成跨网站、应用和文件的长时任务。当前基准（如 Odysseys）日益强调长时、多步骤工作流，而单智能体串行执行会产生长轨迹、上下文累积和更多错误机会，因此自然想到采用多智能体并行分解。
- **关键物理瓶颈**：多智能体 CUA 系统中，子任务在不同的虚拟机（VM）上并行执行，但**两个 VM 的实时状态无法合并**——VM 状态包含浏览器标签、cookies、登录会话、GUI 窗口、剪贴板、文件系统变更和进程状态等，主流虚拟化技术（VMware、KVM/QEMU 等）只支持从单个父 VM 克隆（clone）或快照，没有融合两个运行中机器的操作。论文将此约束命名为 **单父 VM 继承（single-parent VM inheritance）**。
- **现有方法的不足**：现有多智能体 CUA 系统要么在单一环境中串行执行（如 Agent S2、CoAct-1），要么并行分解但忽略单父约束（如 MACU）。当多个有状态子任务需要汇聚时，系统被迫保留一个 VM、丢弃其他 VM 并重建丢失状态，或运行时修改计划——这些均属临时性（ad-hoc）处理。
- **论文的定位**：将单父 VM 继承约束作为**一级规划约束**（first-class planning constraint）显式建模，而非事后补救，从而让多智能体 CUA 系统能够高效扩展。

## 2. 方法论：Spine-Branch Coordination

- **核心设计原则**：**状态不可廉价重建的工作沿"主干"（Spine）连续流动；一切可降为可传递工件（artifact）的工作并行在"分支"（Branch）上执行**。
- **图表示**：任务被表示为角色类型化的依赖 DAG：$G = (V, E_{vm}, E_{art}, \rho)$，其中：
  - $V = W \cup \{a\}$，$W$ 为 CUA 工作节点集合，$a$ 为 Manager 执行的聚合节点；
  - $E_{vm}$ 为 VM 状态依赖边（`init_from`），连接 spine 节点；
  - $E_{art}$ 为工件依赖边，可连接任意节点；
  - $\rho: W \to \{\text{SPINE}, \text{BRANCH}\}$ 分配角色。
- **结构性约束**（公式 (2)）：
  - $\deg^-_{E_{vm}}(v) \le 1$——每个节点最多一个 VM 父节点（单父继承）；
  - $\deg^+_{E_{vm}}(b) = 0, \forall b \in B$——分支 VM 不向后传递状态（将被丢弃）；
  - $\deg^+_{E_{art}}(b) \ge 1, \forall b \in B$——每个分支必须产出至少一个工件。
- **三种角色**：
  - **Manager**：纯推理 LLM，不执行 GUI 操作。负责初始分解（构建 G）、确定 spine、分配角色；最终执行聚合节点 $a$，结合最后 spine 节点的 VM 和收集到的工件合成最终响应。
  - **Spine Workers**：沿 $S = (s_1 \to \cdots \to s_k)$ 序列执行，$s_1$ 从全新 VM 启动，$s_{i+1}$ 通过 `init_from` 继承 $s_i$ 的最终 VM 状态。负责保存和扩展登录会话、打开的应用程序、部分完成的 GUI 工作流等昂贵状态。
  - **Branch Workers**：在全新 VM 或 spine VM 克隆上并行执行，完成后提交至少一个可提取工件，VM 随即被丢弃。
- **通信通道**：
  - **活动状态通道（Live-state Channel）**：沿 $E_{vm}$ 边通过 VM 克隆传递状态，每个节点至多一个父节点；
  - **工件通道（Artifact Channel）**：沿 $E_{art}$ 边直接传输文件、文本等可提取交付物，支持任意扇形输入/输出，不依赖 Manager 中转。
- **调度与上下文本地化**：固定容量 $K$ 个并发 CUA；节点在其依赖全部完成后就绪，有槽位即启动；每个 worker 只接收局部指令和所需工件，避免完整截图与动作历史累积在单一上下文，减少长时执行中的陈旧观测干扰。
- **Step-Budget Prompting（SBP）**：在 CUA 执行循环中按已用步数比例 $r_t = t/M$ 注入三种递进的提示：
  - $0 \le r_t < \frac{1}{2}$：效率模式（避免重复动作）；
  - $\frac{1}{2} \le r_t < \frac{3}{4}$：提交模式（优先完成交付物）；
  - $\frac{3}{4} \le r_t < 1$：收尾模式（立即提交最佳可得结果）。
  
  该机制保证分支在步数预算耗尽前提交工件，不增加额外智能体、工具或模型调用。
- **算法流程**（Algorithm 1）：Manager 规划出图 G → 调度器循环执行"弹出就绪节点→克隆或新建 VM→注入工件→启动 worker"，任一 worker 完成后标记完成、收集工件、丢弃分支 VM → 最终 Manager 聚合。

## 6. 主要结论与发现

- **主结果**：Spine-Branch 在三种骨干上均优于 MACU：
  - Success Rate：+6.0%（gpt-5.4-mini）至 +16.5%（Qwen3.7-Plus）；
  - Rubric Average：+4.7 至 +12.9 个百分点；
  - 每任务成本降低：34%–70%。
- **强骨干上的退化逆转**：最强骨干 Qwen3.7-Plus 上，MACU 不仅未超过单智能体（50.5% vs. 55.0%），反而退步；Spine-Branch 将其推至 67.0% SR，说明显式状态连续性是解锁强模型 test-time scaling 的关键。
- **难度维度**：Spine-Branch 的优势在 hard 任务上最突出；Qwen3.7-Plus 上甚至 hard 成功率（65.1%）超过 medium（60.9%），而 Single-Agent 和 MACU 随任务长度增加急剧退化。
- **消融结论**：
  - 移除 spine 或 branches 均降低性能；移除 spine 损失更大（SR 73.3%→66.7%），说明状态连续性价值更高；完整框架以更少动作实现最高准确率；
  - SBP 在 Spine-Branch 上一致有效，主要机制是"防止截断损失"（节省 token）与"拯救被放弃的任务"（增加 token），后者仅出现在弱骨干上；
  - 弱 Manager（gpt-5.4-mini）使性能下降 0.07–0.14 macro score，但分解结构依然稳健，且大多数骨干上仍优于 Single-Agent。
- **失败模式**：非完美轨迹中 35% 为环境阻塞（反爬虫/CAPTCHA 25%、网站不可达 10%），65% 为 CUA 能力不足（指令跟随失败 29%、过早停止 15%、跳步 8%、路径浪费 8%、数据捏造 6%）——协调层未引入额外失败模式。
- **OSWorld 2.0**：分解在这些 GUI 任务上通常不值得——Single-Agent 获得更高奖励（0.22 vs. 0.16）且无超时；但过滤掉琐碎分解后，值得分解的任务子集（19 个）上 Spine-Branch 反超（0.17 vs. 0.12），说明"何时分解"本身是一个重要能力。
- **效率归因**：Spine-Branch 的 Manager token 开销约为 MACU 的五分之一（115K vs. 653K tokens），因为信息沿 spine/artifact 通道直接流动，无需 Manager 中转。

## 7. 优点

- **问题建模新颖且物理合理**：将 VM 状态不可合并这一虚拟化层的物理事实提炼为"单父 VM 继承"约束，并升级为规划图的一级约束，理论表述清晰（公式 1–3）。
- **结构简洁优雅**：一条脊柱承载状态、多个分支并行取工件，从构造上避免 VM 合并，无需运行时重规划；图结构天然 DAG，存在合法拓扑执行序。
- **通信去中心化**：Manager 只做初始规划和最终聚合，不承担信息中转，大幅削减 Manager token 开销（约 5 倍），避免长上下文瓶颈。
- **上下文本地化**：每个 worker 只见局部指令和所需工件，减少长轨迹中的陈旧观测干扰。
- **SBP 设计轻量普适**：不增加任何智能体/工具/模型调用，仅注入几条递增提示即可防止分支进度随 VM 销毁而丢失，且理论上有普适性。
- **实验严谨**：三种骨干覆盖弱/中/强能力层次；统一评估协议（rubric judge、标准方差）；消融设计系统性隔离 spine、branches、SBP、Manager 质量的贡献。
- **坦率的负面结果报告**：OSWorld 2.0 上揭示分解未必值得，并提炼出"并行化独立且非平凡任务"的实用原则，体现科研诚信。

- **基准覆盖单一**：主实验集中在 Odysseys 一个基准上；OSWorld 2.0 仅做滤波

## 8. 不足与局限（续）

- **OSWorld 2.0 仅做滤波**后仅评估 65 个可分解任务，未覆盖完整基准；其中 21 个任务因墙钟超时（60 分钟子任务限制）被迫终止并拉低平均奖励，而并行启动本身更易受该时限影响，结论在更宽松时限下未必成立；"过滤掉琐碎分解后反超"的子集仅 19 个任务，统计说服力有限。
- **分支状态不可挽救**：分支 VM 一旦销毁，其未提交的中间状态（半填写的表单、未保存的登录会话等）永久丢失。若 Manager 最初对分支/脊柱的划分有误，事后无法将分支升级为脊柱节点，也无法从脊柱动态拆出新的分支——结构一经确定便固定，缺少运行时重规划的兜底能力。
- **对分解质量的量化缺失**：Manager 的分解正确性未被单独评估，也没有"是否值得分解"的前置判据；论文仅在 OSWorld 2.0 上事后观察到"琐碎分解无益"，却未将其建模为可预测的决策问题。
- **环境阻塞问题悬而未决**：约 35% 的失败源于反爬虫/CAPTCHA、网站不可达等环境因素，系统未提出任何针对性缓解手段；这类失败与协调策略无关，意味着任何 CUA 系统在这些任务上都会触及外部可用性天花板。
- **统计功效与分析粒度不足**：主实验仅报告三次运行的标准差，未给出置信区间、效应量或成对显著性检验；45 任务消融子集较小，SR 数个百分点内的差异难以判定显著；不同难度、不同骨干内部的详细误差分析也较粗。
- **缺乏跨领域泛化证据**：实证范围限于 GUI 截图环境（Odysseys、OSWorld 2.0），未在代码仓库、文档处理或其他 agentic 基准上验证；单父继承约束虽具物理普遍性，但其在非 VM 环境（如容器、远程浏览器会话）中的适用性未做讨论。
- **成本估算口径有限**：报告了 per-task API 费用与 token 消耗，但未披露本地 Qwen3.6-27B 推理的硬件占用、端到端 wall-clock 时间对比（除 OSWorld 的筛选外）、或大规模并发下的调度开销，难以完整评估工程落地成本。

## 9. 总体评价与展望

- 这是一篇**问题动机敏锐、约束抽象准确、方法设计优雅**的系统性论文。核心贡献不在于提出更强的单智能体 CUA，而在于把虚拟化层的物理事实（VM 状态不可合并）提炼为"单父 VM 继承"这一可计算的规划约束，并给出"脊柱保状态、分支取工件"的简洁结构，从构造上避免了状态合并难题，同时通过去中心化通信和上下文本地化获得了显著的效率收益。
- 两点最具学术价值的启发：(1) **"何时分解、如何接合状态"应作为一等公民问题显式建模**，而非事后再规划；(2) **轻量机制（如 SBP）可在不增加任何模型/工具调用成本的前提下**，显著提升并行子智能体的产出可靠性，这对 test-time scaling 的工程实践有直接借鉴意义。
- 未来有前景的方向：递归 Spine-Branch（分支内部允许局部脊柱，支持更深层并行）；分解价值预估器（预测某任务是否值得开分支，从根源回答"何时分解"）；将单父继承约束推广到跨主机、跨组织、多设备等更广义的 agent 协作场景；以及引入动态角色晋升机制，为初期分解错误提供运行时修正通道。
