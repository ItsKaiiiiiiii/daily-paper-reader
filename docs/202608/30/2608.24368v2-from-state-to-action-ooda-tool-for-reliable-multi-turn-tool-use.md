## 摘要
可靠的多轮工具使用要求智能体保持不断演化的任务状态，并确保每个动作与其保持一致。然而，直接的函数调用和ReAct式策略在同一自回归轨迹中学习状态追踪和动作生成。这种耦合造成了状态-动作竞争：生成下一次调用的压力可能会覆盖或忽略交互早期积累的信息。受博伊德观察-定向-决策-行动循环的启发，我们引入了OODA-Tool，一种类型化的闭环策略，通过将状态保持与动作实现分离来缓解这种竞争。OODA-Tool并非直接从交互历史生成动作，而是将每个决策通过控制器检查的中间状态进行路由，确保最终输出仍然基于当前任务状态。具体而言，观察阶段重建任务状态，定向阶段确定是否应执行，决策阶段形成可接受的动作结构，行动阶段实现外部输出。我们使用从0.6B到14B的Qwen3模型，在多轮、多工具和不完整信息设置下，将OODA-Tool与直接函数调用和ReAct策略进行了评估。OODA-Tool在不同模型规模上持续提高了任务成功率，在较小模型以及动作强烈依赖于跨轮次和先前工具结果累积信息的任务上提升更大。受控变体、阶段级消融和迁移评估进一步证明了这些改进的稳健性。

## Abstract
Reliable multi-turn tool use requires an agent to preserve an evolving task state and ensure that each action remains consistent with it. However, direct function-calling and ReAct-style policies learn state tracking and action generation within the same autoregressive trajectory. This coupling creates state-action competition: the pressure to produce the next call can overwrite or ignore information accumulated earlier in the interaction. Inspired by Boyd's Observe-Orient-Decide-Act cycle, we introduce OODA-Tool, a typed closed-loop policy designed to mitigate this competition by separating state preservation from action realization. Rather than generating an action directly from the interaction history, OODA-Tool routes each decision through controller-checked intermediate states, ensuring that the final output remains grounded in the current task state. Specifically, Observe reconstructs the task state, Orient determines whether execution is warranted, Decide forms an admissible action structure, and Act realizes the external output. We evaluate OODA-Tool against direct function-calling and ReAct policies using Qwen3 models ranging from 0.6B to 14B across multi-turn, multi-tool, and incomplete-information settings. OODA-Tool consistently improves task success across model sizes, with larger gains on smaller models and on tasks whose actions depend strongly on information accumulated across turns and prior tool results. Controlled variants, stage-level ablations, and transfer evaluations further demonstrate the robustness of these improvements.

## 1. 核心问题与整体含义

- **研究背景**：语言模型智能体越来越多地依靠搜索引擎、数据库、代码执行器等外部工具完成超出参数知识范围的任务。多轮工具使用中，每次调用的合法性取决于一个随任务推进而不断变化的交互状态。
- **核心问题**：现有方法（直接函数调用、ReAct 式策略）将状态跟踪与动作生成耦合在同一个自回归轨迹中，导致论文所称的 **“状态-动作竞争”**——模型生成下一动作的压力会覆盖或忽略交互早期积累的状态信息，表现为：
  - 丢失先前的约束和状态；
  - 过早调用工具或基于未经验证的依据发起调用。
- **整体含义**：该论文主张将“状态保持”与“动作实现”显式分离，用带类型检查的中间状态约束决策过程，使每个外部输出都建立在可核查的当前任务状态之上。

## 2. 方法论

- **核心思想**：借鉴 Boyd 的 **OODA（Observe–Orient–Decide–Act）闭环循环**，将单次决策分解为四个带类型接口的阶段，并由中央控制器检查各阶段交接：
  - **Observe（观察）**：从交互历史重建“携带来源信息的任务状态”，记录目标、实体、活动槽位、约束、未完成子目标、近期工具事实、状态变化等；
  - **Orient（定向）**：判断当前状态是否足以执行，输出五种响应模式之一：`SOLVABLE_WITH_TOOL`、`NEED_CLARIFICATION`、`RESPOND_DIRECTLY`、`RECOVER_FROM_FAILURE`、`DONE`；同时记录缺失槽位、违反约束和不可用的工具；
  - **Decide（决策）**：在 Orient 许可的范围内构造动作结构（单次调用、顺序链或并行集合），指明目标工具、调用顺序与数据依赖，但不展开最终参数值；
  - **Act（行动）**：将动作结构编译为 schema 合法的可执行调用，绑定来自任务状态或工具返回的参数值，或输出经授权的自然语言响应。
- **关键约束（公式/逻辑）**：中央控制器强制 `z_Dt ∈ Z_D(z_Rt)`，即决策阶段不能授权与定向阶段冲突的动作结构；运行时还执行 schema、依赖与 grounding 校验。
- **策略变体**：
  - *Joint OODA*：一次调用内串行输出四个阶段；
  - *Shared OODA*：同一 LoRA 适配器分四次阶段调用；
  - *Specialized OODA*：每个阶段使用独立的 LoRA 适配器。
- **监督目标构造**：训练标签按阶段顺序生成，且严格防止信息泄漏——当前轮的标注仅使用可见的历史前缀，排除未来用户轮次、当前动作的观察结果及其揭示的信息。
- **状态充分性检验**：通过“typed-state bottleneck”移除下游阶段的历史访问权限，只保留类型化上游状态，检验 Observe 状态是否保留了足够信息支持后续决策。

## 6. 主要结论与发现

- **RQ1（是否有效）**：Specialized OODA 在所有模型规模上均取得最高 Task Success；模型越小增益越大（如 0.6B 上比 Direct-LoRA 高 6.86 个点，14B 上高 4.48 个点）。Joint → Shared → Specialized 的递进说明多遍分解与阶段专用适配器均有贡献。
- **RQ2（何时最有效）**：增益集中在**状态密集型场景**——长历史、信息缺失、状态变化、活跃约束、深层工具依赖；对**并行调用**场景增益很小（1.7B 上仅 +3.2pp，而状态类约为 +13 至 +16pp）。
- **RQ3（哪些组件关键）**：去除 Orient 造成最大性能下降；Decide–Act 分离在信息缺失和多工具场景尤其重要；类型化状态优于自由文本中间状态；阶段专用适配器贡献相对较小。
- **RQ4（迁移与代价）**：OODA 在 FAIL-TaLMs 和 MTU-Bench 上有正迁移但幅度温和，在 BFCL 上对小模型增益明显；代价是推理延迟约为 Direct-LoRA 的 2.36 倍。
- **RQ5（状态是否可支撑动作）**：类型化状态能支撑下游动作；OODA Specialized 的 SACR 显著低于 Joint（3.9% vs. 7.8%）；加强约束策略可消除过期值绑定问题，并提高阶段间梯度对齐。
- **RQ6（参数 grounding）**：以 ToolDial 案例说明，OODA 能通过显式的支持链避免“选对了地点却拷错标识符字段”的错误。

## 7. 优点

- **问题定义清晰**：提出“状态-动作竞争”这一可操作的失败模式，并给出可验证的 SACR 等诊断指标。

- **可解释性好**：阶段输出是显式、可检查的，便于错误溯源和运行时校验。

## 8. 不足与局限
