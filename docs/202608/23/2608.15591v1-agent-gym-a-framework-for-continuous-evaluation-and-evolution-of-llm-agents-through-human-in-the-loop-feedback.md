## 摘要
生产环境中部署的大型语言模型（LLM）智能体面临一个根本性矛盾：智能体的行为在部署时被冻结，而它必须处理的业务规则和边缘情况却在持续演变。现有方法解决了智能体构建和一次性评估的问题，但缺乏在不修改智能体源代码的情况下，对部署后行为进行持续修正的结构化机制。市场上提供的大多数方法需要大量收集日志和追踪信息，并由工程团队重新审查智能体设计，这一过程繁琐、耗时，并且削弱了智能体转型的经济价值。我们提出Agent Gym，一个模块化的、与领域无关的框架，它将任何基于LLM的现有智能体包裹在一个持续评估与演进的循环中。该框架提供六种可组合的能力——行动（Act）、评估（Evaluate）、调查（Investigate）、修正（Correct）、学习（Learn）和观察（Observe）——并组织在三个架构区域中：一个将领域知识编码到配置工件中的宪法层，一个将行动、调查和自适应修正串联起来的运行时推理流水线，以及一个使领域专家能够通过自然语言交互发现和验证新修正规则的学习循环。关键技术贡献包括：一个具有21个条件运算符和三层动作的混合确定性-LLM修正引擎，一个用于无真实标签合规验证的三层调查架构，以及一个在人工批准之前保证规则正确性的程序化安全循环。我们进一步引入了规范-笔记差距（Spec-to-Note Gap），这是一种受自动编码器启发的智能体系统透明度视角。一个用于发票处理的开源参考实现表明该框架完全可操作并可供采用。

## Abstract
Large Language Model (LLM) agents deployed in production environments face a fundamental tension: the agent's behavior is frozen at deployment time, while the business rules and edge cases it must handle continue to evolve. Existing approaches address agent construction and one-time evaluation but provide no structured mechanism for continuous post-deployment behavioral correction without modifying the agent's source code. Most of the approaches offered in the market, require intense collection of logs and traces, and re-examining the agent design by the engineering team, a process which is heavy, long and negates the economical value of agentic transformation. We introduce Agent Gym, a modular, domain-agnostic framework that wraps any existing LLM-based agent in a continuous evaluation-and-evolution loop. The framework provides six composable capabilities --- Act, Evaluate, Investigate, Correct, Learn, and Observe --- organized across three architectural zones: a constitution layer that codifies domain knowledge in configuration artifacts, a runtime inference pipeline that chains acting, investigation, and adaptive correction, and a learning loop that enables subject matter experts to discover and validate new correction rules through natural language interaction. The key technical contributions include a hybrid deterministic-LLM correction engine with 21 condition operators and three-tier actions, a three-layer investigation architecture for ground-truth-free compliance validation, and a programmatic safety loop that guarantees rule correctness before human approval. We further introduce the Spec-to-Note Gap, an autoencoder-inspired view of agentic system transparency. An open-source reference implementation for invoice processing demonstrates that the framework is fully operational and ready for adoption.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题：静态智能体困境（static agent dilemma）**。LLM智能体在生产环境部署后，其行为即被“冻结”，而它必须应对的业务规则、法规要求和边缘案例却在持续变化，两者之间存在根本性矛盾。
- **三类生产失败的催生**：
  - **边缘案例失败**：智能体遇到训练数据中未出现的文档配置或法规例外；
  - **系统性误解**：智能体对某一整类案例持续错误地应用某条业务规则；
  - **漂移与规则演化**：业务规则随时间变化，而智能体缺乏吸收这些变化的机制，除非修改源代码。
- **现有路径的痛点**：从“领域专家（SME）发现问题”到“智能体行为得到修正”，传统路径需经过软件工程瓶颈——SME非正式描述问题→工程师解读→修改代码或提示词→重新部署→SME验证。这一流程缓慢、信息有损、易出错且难以规模化。市场上多数方案需大量收集日志和追踪数据、由工程团队重审智能体设计，流程重、周期长，削弱了智能体转型的经济价值。
- **评估的另一挑战**：传统评估框架将智能体输出与标注的真实值（ground truth）对比，但生产环境中新型案例往往不存在真实值，即便有参考数据也未必能反映隐含的业务规则。因此需要**双重评估模型**：有真实值时验证参考数据一致性，无真实值时验证决策是否符合业务规则本身。

## 2. 论文提出的方法论

### 2.1 总体框架

- 提出 **Agent Gym**——一个模块化、领域无关的框架，将任意现有LLM智能体包裹在**持续评估-演进循环**中，无需修改智能体源代码，对智能体内部结构零假设，仅观察输入-输出行为。
- 提供**六种可组合能力**：Act（行动）、Evaluate（评估）、Investigate（调查）、Correct（修正）、Learn（学习）、Observe（观察）。
- 架构划分为**三个区域**：

### 2.2 Zone 1——宪法架构（Constitution Architecture）

- 由两个声明式配置工件构成，这是领域知识唯一的存储位置，也是框架领域无关性的关键：
  - **主数据（Master Data）**：结构化YAML文档，涵盖11个部分（文档类型、提取模式、分类法、验证流水线定义、输出模式、评估比较组、调查文件映射、配置默认值、域特定检测逻辑、工件命名约定、拒绝模板）；
  - **规则书（Rules Book）**：人类可读的Markdown文档，捕获治理智能体处理逻辑的完整业务规则。调查智能体将其作为LLM验证的上下文。
- **Bootstrap Agent**（计划中的自动化）：四阶段LLM流水线，通过分析智能体源代码和示例输出来生成上述两个工件；当前参考实现使用手动编写的工件。

### 2.3 Zone 2——运行时推理管道

- **三层流水线**：行动智能体（Acting Agent）→ 调查智能体（Investigation Agent）→ ALF修正引擎。
- **行动智能体**：仅要求输出JSON工件，其余架构不受约束。
- **调查智能体（三层验证架构，支持无真实值合规验证）**：
  - **Layer 1——确定性检查**：数据源验证（字段值来源是否正确）、绕过检测（是否跳过了必需验证步骤），无LLM调用；
  - **Layer 2——LLM规则发现**：初始化时将规则书发送给LLM，发现并分类验证规则，用规则书内容的SHA-256哈希进行缓存，规则书未变则后续运行跳过；
  - **Layer 3——保守交叉验证**：对每个规则组逐一评估，检测到潜在违规时触发**三重检查机制**（重新运行两次），仅三次独立运行都确认的违规才被报告，大幅降低误报率。
- **成本控制四机制**：内容哈希缓存、按节过滤上下文（只发送当前验证阶段相关的规则书章节）、批处理分组（确定性规则组合并为一次LLM调用）、三重检查早退（仅第一次调用检测到潜在违规时才发起后续验证）。
- 产出**合规分数（0–100%）**，分为：Fully_Compliant（≥80%）、Partial_Violation（60–80%）、Major_Violation（<60%）。重大违规会**中止流水线**，阻止不合规输出进入修正阶段。
- **ALF（自适应学习框架）——混合确定性-LLM修正引擎**：
  - **检测与修正分离**：检测完全确定性（21个条件运算符，包括相等、包含、正则匹配、数值比较、列表成员、空值检查、前缀匹配、动态字段引用等，AND逻辑连接，零LLM参与、完全可复现）；修正根据场景需要调用LLM。
  - **三层动作模型**：Tier 1字段编辑（正确值为已知常量时的确定性编辑）；Tier 2外科补丁（LLM确定目标字段值并补丁到现有输出）；Tier 3流水线继续（智能体提前终止时，LLM从恢复点继续执行以生成完整修正输出）。
  - **Collect-Plan-Execute聚合管道**：收集所有匹配规则→按层级合并为修订计划→按固定顺序执行（Tier 3→Tier 2→Tier 1）；基于作用域的互斥保证每个作用域至多一条规则触发，每个案例最多2次LLM调用；全程保留完整审计轨迹（评估了哪些规则、哪些匹配、修订计划、LLM元数据）。

### 2.4 Zone 3——学习与演进循环

- **学习智能体**使SME能以自然语言描述期望的修正，协作发现新ALF规则。四个子模块：
  - **Case Loader**：展示特定案例的智能体输出、分阶段验证结果、提取数据和修正历史；
  - **Rule Discoverer**：接受SME自然语言反馈，结合案例数据、现有规则和规则书解释反馈，生成候选条件，遵循“保守领域原则”（条件足够窄以只匹配目标案例，但足够泛化以覆盖未来相似案例）；
  - **Impact Assessor**：对现有案例样本（始终包含目标案例）确定性评估候选规则，报告目标匹配、附带匹配和安全非匹配；
  - **Rule Writer**：验证模式、检查冲突、备份规则库、持久化已批准规则并附带完整元数据。
- **程序化安全循环（关键创新）**：以代码强制实现（而非提示词指令），LLM无法绕过。每个候选规则经历迭代验证循环：模式验证→目标匹配验证（失败则LLM自动放宽条件但保持保守）→附带影响评估（发现意外匹配则LLM自动收紧条件，如增加供应商名称、金额范围、服务类别）→SME审批→持久化。循环最多重复3次，附带影响持续存在则向SME警告。未经人类明确批准，任何规则不会被应用。
- **规则生命周期管理**：启用/停用标志（保留审计历史）、时间戳备份（任意修改前）、冲突检测（重复标识、优先级冲突、作用域重叠）、结构化元数据（严重度、根因、规则书章节）支持查询过滤；规则可永久删除（先备份）。

### 2.5 评估引擎

- 真实值可用时：**两层定量评估**——（1）确定性字段级比较（基于配置的比较组，数值字段默认财务容差$0.02，文本字段归一化后精确匹配）；（2）LLM-as-judge（可选，输出Aligned/Partially_Aligned/Not_Aligned整体对齐判定）。两者均从主数据YAML读取配置，新增比较组仅需改YAML。

### 2.6 Spec-to-Note Gap（规范-笔记差距）

- 受自动编码器启发的系统级透明度视角：规范（输入）→实现代码/系统（潜在表示）→LLM审计器生成透明性笔记（重建输出）。规范与笔记之间的对比作为**重建损失**，暴露缺失能力、无声的范围蔓延和评估套件从未衡量的行为。该概念将round-trip correctness（Allamanis et al., 2024）从函数级一致性推广到整个系统粒度，连接了Model Cards与Datasheets的文献传统。

## 7. 优点

- **对智能体的非侵入式设计**：将智能体视为黑盒，修正分层应用（原始输出保留、修正输出并列），保证可审计性和独立回滚能力。
- **架构的领域无关性**：所有领域知识集中在YAML+Markdown配置工件中，采用新领域只需更换配置，框架代码完全不动；宪法工件同时充当人类可读文档和机器可解析规范。
- **检测与修正的巧妙分离**：检测完全确定性（零LLM、完全可复现），修正按需使用LLM，兼顾可靠性与灵活性；Collect-Plan-Execute机制保证每个案例至多2次LLM调用、规则无冲突。
- **程序化安全循环**：在代码层面强制规则验证（模式→目标覆盖→附带影响→自动收紧），而非依赖LLM的提示词自觉，配合SME审批，具备强治理保障；分级的治理权限（SME批准案例级规则 vs. 多利益相关方批准宪法修改）防止恶意规则注入和越权策略漂移。
- **成本控制的工程化设计**：SHA-256缓存、按节过滤、批处理、早退机制务实且针对生产环境痛点。
- **无真实值合规验证**的三层调查架构是生产环境评估的重要创新，填补了传统ground-truth评估在生产场景中的空白。
- 提供**开源参考实现**，可复现、可扩展。

- **引导流程仍为手动**：Bootstrap Agent（自动生成宪法工件）仅是计划中的自动化，当前采用手动编写，影响新领域上手的效率。
- **单域验证**：参考实现仅覆盖发票处理，领域无关性主张缺乏多域实证支撑。
- **LLM成本未量化**：调查智能体的成本控制机制虽合理，但缺少大规模部署下的实测成本降低数据。
- **规则生命周期管理不完整**：规则的晋升（promotion）机制（将频繁命中的修正规则迁入行动智能体永久逻辑）尚未自动化；定期审查、逐规则性能跟踪、日落策略、规则合并等功能仍属未来工作。
- **观察（Observe）能力未实现**：运维仪表盘计划在后续版本提供。
- **Spec-to-Note Gap为概念性提议**：未在真实系统上做实例化验证，审计器自身的忠实度度量、笔记重新生成时机等问题悬而未决。
- **实验效度**：无消融实验（如各成本控制机制的实际收益、三重检查的误报率降低程度）、无与传统方法（如人工日志重审流程）的定量对比，报告的多为框架属性而非性能指标。
