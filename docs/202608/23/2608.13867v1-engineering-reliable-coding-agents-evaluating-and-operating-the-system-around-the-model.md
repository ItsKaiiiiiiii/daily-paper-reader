## 摘要
AI 编码代理通常作为模型进行评估，但作为系统进行部署。其可靠性不仅取决于模型能力，还取决于运行框架、执行状态、检索、记忆与状态管理、权限、审查界面以及资源分配。本专著考察这些边界，并开发一个用于可靠评估和运维编码代理的框架。它通过结构化的多声部综述、针对性更新审计、软件工程覆盖分析和分布式系统证据综合，综合了 164 篇学术著作、100 条实践者记录、29 条基准测试记录和 17 条作者系统案例记录。在这些证据中，许多表面上的模型失败实际上源于系统其他部分，而某一层的改进往往无法传播到端到端的结果。评估和运维被视为一个依赖链，其中任务构建、执行环境、检索、状态管理、验证或可观测性中的弱点会使下游结论失效。该专著贡献了一个版本化的 206 条可靠性记录目录：193 项门控实践（其中 56 项得到深入发展），外加 13 条研究线索；一份证据台账；一个跨代理生命周期的依赖与修复不对称性框架；来自实际运维代理系统的测量和失败案例；可运行的评估和可靠性协议；以及五个带证据图谱的可复用代理技能。这些共同提供了一种系统级方法论，用于区分模型能力与基础设施效应、设计可辩护的评估，以及构建在组件故障时能安全恢复的系统。该综述是结构化而非详尽无遗的，证据强度因主题而异，结果取决于工作负载和配置。这些方法记录了哪些搜索通道已执行、哪些仍未执行，以及证据分级主张的局限性。

## Abstract
AI coding agents are commonly evaluated as models but deployed as systems. Their reliability depends not only on model capability, but on the harness, execution state, retrieval, memory and state management, permissions, review interfaces, and resource allocation. This monograph examines those boundaries and develops a framework for evaluating and operating coding agents reliably. It synthesizes 164 scholarly works, 100 practitioner records, 29 benchmark records, and 17 author-system case records through a structured multivocal review, targeted update audits, software-engineering coverage analysis, and distributed-systems evidence synthesis. Across this evidence, many apparent model failures originate elsewhere in the system, while improvements at one layer often fail to propagate to end-to-end outcomes. Evaluation and operation are treated as a dependency chain in which weaknesses in task construction, execution environments, retrieval, state management, verification, or observability can invalidate downstream conclusions. The monograph contributes a versioned catalog of 206 reliability records: 193 gated practices, including 56 developed in depth, plus 13 research leads; an evidence ledger; a framework for dependency and repair asymmetry across the agent lifecycle; measurements and failure cases from operated agent systems; runnable evaluation and reliability protocols; and five reusable agent skills with evidence maps. Together, these provide a system-level methodology for distinguishing model capability from infrastructure effects, designing defensible evaluations, and building systems that recover safely when components fail. The review is structured rather than exhaustive, evidence strength varies by topic, and results depend on workload and configuration. The methods record which search lanes were executed, which remain unexecuted, and limits on evidence-grading claims.

## 1. 核心问题与整体含义

- **核心问题**：AI 编码代理（coding agents）通常被**当作模型来评估**，却被**作为系统来部署**（"evaluated as models but deployed as systems"）。这导致了一个根本性的错位——模型的基准分数并不能代表生产环境中的实际可靠性。
- **关键观点**：代理的可靠性不仅取决于模型能力，还取决于模型周围的一整套系统组件，包括：**运行框架（harness）、执行状态、检索机制、记忆与状态管理、权限边界、审查界面、资源分配**等。
- **核心现象**：许多表面上的“模型失败”实际上源自系统其他部分；而在某个层（如检索）测得的改进，往往无法传播到端到端的任务结果——这种"单层改进不传导"的现象贯穿全书。
- **整体含义**：评估与运维必须作为一个**依赖链（dependency chain）**来对待：测量决定分级是否可信，分级决定包含与恢复是否有效，包含与恢复决定检索与上下文是否可用，检索决定审查与问责是否有据，审查决定分配与成本是否合理——**每一层决定了下一层可以信任什么**。
- **修复不对称性（repair asymmetry）**：后期机制往往容易添加，但无法修复上游已经丢失的证据——更多样本无法修复有偏的任务分布，更多裁判无法修复模糊的评分标准，更多代理无法修复把空检索结果当作权威的系统边界。

## 2. 方法论

### 2.1 核心思想
- 将编码代理的生产系统视为一个**"软件工厂"（software factory）**，即一个持久化的分布式系统：接受逻辑工作（logical work）、调度尝试（attempts）、运行工人（workers）、验证产物（artifacts）、发布外部效果（external effects）。
- 区分**逻辑工作 vs 执行尝试**、**租约（lease）vs 写权威（authority）**、**候选产物 vs 已接受完成**、**本地完成记录 vs 外部承诺**、**验证器输出 vs 语义事实**——恢复系统的可靠性取决于这些区分是否清晰。

### 2.2 依赖链框架
- **六层依赖链**（每层为下一层提供证据边界）：
  1. **测量（Measurement）**：判断一个差异是否可信
  2. **分级（Grading）**：将观测转化为接受决策
  3. **包含与恢复（Containment & Recovery）**：执行记录能否在失败后存活且不扩展权限
  4. **检索与上下文（Retrieval & Context）**：哪些证据能到达代理
  5. **审查与问责（Review & Accountability）**：谁能挑战结果、谁控制关键转换
  6. **分配与成本（Allocation & Cost）**：哪个系统获得未来的工作

### 2.3 关键技术细节与方法
- **多声部综述（multivocal review）**：综合 164 篇学术著作、100 条实践者记录、29 条基准记录、17 条作者系统案例记录；同时包含定向更新审计、软件工程覆盖分析（OpenAlex 探针）、分布式系统证据合成。
- **证据分组四层制**：
  - **强证据**：受控对比、已验证基准结果
  - **方向性证据**：支持机制或方向，但不建立完整建议
  - **佐证证据**：案例报告、实践者叙述
  - **无效/冲突证据**：不支持预期效果或限制其他声明
- **可靠性记录目录**：206 条带版本号的记录（ERCA-NNN 格式），其中 193 条为门控实践、13 条为研究线索；目录与正文、证据台账、协议和技能通过稳定标识符互相连接。
- **关键公式与统计方法**：
  - **配对 t 检验**：以配对差异 `d_i = x_i - y_i` 为基础，`SE(¯d) = s_d / √n`，方差公式中通过协方差项 `-2 Cov(x,y)` 消除共享任务难度
  - **Cohen's kappa**：`κ = (observed agreement − expected agreement) / (1 − expected agreement)`，用于校正偶然一致性
  - **pass@1 / pass@k / pass^k**：分别表示单次成功率、至少一次成功概率、所有 k 次全部成功概率
  - **最小可检测效应（MDE）**：在固定方差、错误率下，实验能可靠分辨的最小差异
  - **成本-精度前沿（Pareto frontier）**：要求配置同时按精度和成本选择，消除被支配配置

### 2.4 算法/流程化协议
- **最小可靠性通过（minimum reliability pass）**：六步快速检查，包括重跑一次基于聚合分数的决策、分别记录成本与质量、测试权限边界、从系统状态验证完成声明等。
- **故障注入恢复测试协议**：五个生命周期击杀点（分发前、分发后外部提交前、提交后本地确认前、确认后持久化前、持久化后），配以无效应重复的负对照。
- **固定到达重放协议（fixed-arrival replay）**：重放历史工作流时间线，比较调度策略（先来先服务 vs 简单优先级 vs 加权索引），保留最优间隙与饥饿防护。

## 3. 实验设计

### 3.1 数据集 / 场景 / Benchmark
- **公共基准**：SWE-bench、SWE-bench Verified、HumanEval、LiveCodeBench、LongSWE-Bench、RULER、RepoBench、GRACE 等多类基准被引用和审计。
- **作者自建系统**：
  - **CodeProbe**：从合并的 pull request 中挖掘评估任务，将指令与 ground-truth 提交分离，用原始变更触及的测试作为验证命令
  - **CodeScaleBench**（企业级仓库基准）：370 个配对任务，分为 20 个套件、150 个软件生命周期任务 + 220 个组织级任务；覆盖 46 个主仓库（另有 18 个跨仓库任务组扩展到 56 个仓库）、9 种主要语言，包括 Chromium（约 3500 万行）、Firefox（2000 万行）、LLVM（1500 万行）等大型代码库

### 3.2 主要对比方法
- **重复运行对比**：多配置（如基线 vs 检索增强）在同一任务集上重复跑 3 次以上，用配对差异分析
- **消融实验**：去除某组件后重跑（如无工具/无记忆/无检索条件），要求逐任务记录组件实际使用，而非仅声明"已启用"
- **公共-私有差距审计**：用受控匹配任务集对比公共基准分数与私有未见任务分数
- **检索-生成分段评估**：将检索链分解为可用性→检索→放置→上下文充分性→使用五个阶段，分别打分
- **调度策略对比**：先来先服务 vs 简单优先级 vs 混合规则 vs 四特征加权索引

### 3.3 实验数量与充分性
- 论文覆盖**大量子实验**：60000 条 SWE-bench-Verified 轨迹用于估计运行间方差；1750 条轨迹分析提交与解决率的差距；20 个提示变体测试提示敏感性；370 个配对任务的检索效果对比；11 周 1286 个工作项的调度重放等。
- 作者**明确承认**很多实验是叙事性示例（narrative illustration）而非独立证据；只有少数（如 60,000 轨迹、54 周期自评门控实验、288 次上下文文件消融）是严格受控的强证据。

## 5. 主要结论与发现

- **许多模型层面的失败实际上是系统层面的失败**：如持久化缺失导致重复 pull request、过期租约导致陈旧写入、检索空结果被当作权威、门控失效导致权限绕过等。
- **单纯提高模型能力不足以提升可靠性**：更强模型可以在更弱的执行系统中失败；模型能力并不免除系统任何一条工厂契约义务（如 I1-I11）。
- **评估与运维是不可分割的依赖链**：每一层的弱点都会沿链向下传播，且**下游无法修复上游的证据丢失**。
- **网关必须能改变执行**：记录"已批准"但无法阻止实际执行的网关只是合规剧场（compliance theater）。审计发现许多门控在组件缺失时故障开放（fail-open）。
- **应谨慎看待公共基准分数**：公开分数易受污染、测试预言机缺陷（weak oracle）和工作负载不匹配的影响；SWE-bench Verified 的审计发现 16.4% 的任务存在缺陷测试，导致 OpenAI 撤回依赖该基准的结论。
- **工程控制可以且应该先于流行率证据**：部分高风险实践（如灾难恢复权限隔离）即使没有严格对照实验，也能通过直接可验证的机制论证来证明其价值。
- **低成本基线应始终被优先测试**：直接模型调用 + 简单重试往往能匹敌更复杂的架构（如 Kapoor 等人在函数级编码上的发现）；调度实验中 4 特征加权索引并未显著优于简单优先级（6.70 vs 6.70 小时）。

## 6. 优点

- **系统级视角**：将编码代理从"模型中心"转向"系统中心"，提供完整的依赖链框架和工厂契约（I1-I11），各章节有机衔接，而非孤立的技巧列表。
- **证据透明度高**：明确区分强/方向性/佐证/无效证据，诚实标注作者系统案例为"叙事说明"而非独立证据；提供证据台账、盲审打包（供外部评估者计算 kappa）和公开的搜索通道状态。
- **可操作性**：每个章节都配有可运行的协议（如 minimum-reliability-pass.md、recovery-fault-injection.md、allocation-policy-replay.md）、版本化目录和五个可复用代理技能（评估设计、端到端测试设计、失败模式捕获、聚焦执行、验证的长时实现）。
- **统计严谨性**：强调配对分析、最小可检测效应、功率分析、多重性修正、交叉验证等；对自举重采样单元（任务 vs 仓库 vs 套件）的错误有具体自省案例（370 任务间隔被指出过于乐观）。
- **诚实面对局限**：承认某些部分（如第六部分）是研究议程而非成熟部署指导；披露未执行的搜索通道（ACM DL、IEEE Xplore、Scopus）及其对证据分级的限制。

## 7. 不足与局限

- **证据强度不均**：如第 8 章关于隔离和注入防御的实践在*任何*强证据支持下直接给出建议；第 18-19 章（拓扑选择、调度路由）的大部分证据来自望远镜调度、集群管理和多智能体研究的推断转移，而非软件代理生产数据。
- **作者系统案例的独立性问题**：CodeProbe、CodeScaleBench 等由作者自己建构和运维，在厂商产品上执行测量，存在利益冲突和普遍性风险；作者对此有坦白声明，但并未消除这一限制。
- **实验覆盖的偏差风险**：主要实验集中于大型组织代码库（数百万至数千万行），向小型仓库或公共单仓库基准的迁移需要额外验证；成功/失败记录可能存在选择性（如合并历史忽略被拒绝的工作和事故）。
- **时效性限制**：能力测量（模型版本、基准分数）快速老化；搜索结果不完整（ACM、IEEE、Scopus 未执行），可能遗漏相关文献。
- **部分建议缺乏直接支持**：如"上下文文件 A/B 测试"只有两项无效结果（null result）和一项描述性研究；多项工程控制（如容器化、无网络和隔离状态记录）仅以作者系统说明形式呈现，而非对照实验证据。
- **框架的落地成本**：通过完整门控实践、自动化门控和审查流程构建的生产环境基础设施复杂性高，论文部分承认该问题（如"开始应比这本书更小"），但未提供成本效益的量化分析。
