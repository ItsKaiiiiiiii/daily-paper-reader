## 摘要
多智能体氛围编码有望加速软件开发，但现有基准依赖忽视实际时间和金钱成本的合成环境，混淆推理与沟通，且仅奖励表面完成度。我们引入了多智能体从零开始评估基准MSEval，在真实世界任务上评估多智能体编码。基于10个领域中的10个真实全栈项目，MSEval使用分层需求和确定性评分标准来评分性能。其执行引擎LegoGent测试了10种协作拓扑，其中智能体通过周期性同步间隔进行协调，并通过原生CI/CD管道进行部署。同时，自动评分器TAgent动态探测实现，以联合衡量功能成功、延迟和前缀缓存令牌成本。在100次运行中，MSEval揭示组织拓扑在塑造速度-成本-质量权衡方面与模型能力相媲美。对于相同的任务和模型，改变拓扑会使分数变化超过30分，并使墙钟时间加倍。结构化管道以最高质量最快收敛，而重型管理监督会降低性能。最终，MSEval为衡量多智能体团队实际构建软件的方式建立了严格、可复现的标准。该基准已在https://github.com/robinren03/MSEval发布。

## Abstract
Multi-agent vibe coding promises to accelerate software development, yet existing benchmarks rely on synthetic environments that ignore practical time and monetary costs, conflate reasoning with communication, and reward only superficial completion. We introduce multi-agent from-scratch evaluation benchmark, MSEval, evaluating multi-agent coding on real-world tasks. Grounded in 10 authentic, full-stack projects across 10 domains, MSEval scores performance using hierarchical requirements and deterministic rubrics.   Its execution engine, LegoGent, tests 10 collaboration topologies where agents coordinate via periodic sync intervals and deploy through native CI/CD pipelines. Concurrently, the automated grader TAgent dynamically probes implementations to jointly measure functional success, latency, and prefix-cached token cost. Across 100 runs, MSEval reveals that organizational topology rivals model capability in shaping the speed--cost--quality trade-off. For identical tasks and models, varying the topology shifts scores by over 30 points and doubles wall-clock time. Structured pipelines converge fastest with the highest quality, whereas heavy managerial oversight degrades performance. Ultimately, MSEval establishes a rigorous, reproducible standard for measuring how multi-agent teams actually build software. The benchmark is released at https://github.com/robinren03/MSEval.

### 1. 论文的核心问题与整体含义（研究动机和背景）

- **研究背景**：前沿编码智能体已从玩具级函数合成迈向长周期、可执行的软件工程任务。然而，现有编码基准（如SWE-bench、RepoBench等）主要评估**单个智能体**的修补能力或补丁有效性，无法回答实践中日益重要的问题：一个**智能体团队**如何分工、如何从零构建项目、花费多少时间与令牌（token）、如何在具体反馈后改进。
- **核心问题**：多智能体系统承诺通过并行化加速软件开发，但这种承诺是脆弱的——无界通信会放大语义漂移，重型编排可能成为瓶颈，自我报告完成往往脱离可运行行为。现有基准无法隔离“弱编码能力”“重复工作”“上下文陈旧”“交接不良”“部署摩擦”等因素。
- **论文的关键洞见**：**协作拓扑（collaboration topology）**——即团队如何划分工作、谁拥有哪个工件、何时交接、谁能拒绝完成声明、反馈如何路由——应当作为评估的“一等公民”（first-class citizen），与模型能力同等重要。
- **MSEval的定位**：提出一个从零开始的多智能体编码评估基准，基于真实世界的软件工程任务，联合度量**质量、速度与成本**三者间的权衡。核心主张是：对于相同的任务和模型，仅改变拓扑即可使得分变化超过30分，并使墙钟时间翻倍。

### 2. 论文提出的方法论：核心思想、关键技术细节

#### 核心思想
将“协作模式”作为唯一自变量，固定项目、模型、部署路径和评分标准，使拓扑的影响可测量而非偶然。

#### 三阶段流水线
**（1）数据基础**：从大学软件工程课程中筛选10个全栈项目，每个需求文档分解为6-8个模块、30-45个加权条款，归一化为100分制的确定性评分标准。

**（2）LegoGent执行引擎**：将协作模式转化为可执行的智能体团队。
- 每个智能体作为隔离、可恢复的进程运行，拥有文件和shell工具。
- **周期性同步循环**：每4分钟收集各智能体的进度快照（已完成工作、测试证据、阻塞项、下一步计划），并广播合并后的团队视图。
- **活跃邮箱**：支持同步间隔内的定向提问和交接。
- **完成门控**：仅当所有智能体空闲且必需工件就绪时才接受轮次结束。
- **模式模板**：每个协作模式定义四个对象——所有权映射（ownership map）、激活调度（activation schedule）、决策规则（decision rule）、必需交接工件（required handoff artifact）。

**（3）TAgent自动评估器**：充当自动化助教。
- 将原始需求文档解析为结构化YAML评分标准（带权重的情景与通过/部分/失败标准）。
- **表面发现**：从URL和源码重构路由表面（优先使用OpenAPI/Swagger），探测真实契约。
- **三类评估器**：
  - **UI**：Playwright驱动真实站点，读取可访问性树/DOM，判断状态。
  - **API**：认证HTTP序列探测路由，存储请求/响应作为证据。
  - **Code**：目录过滤+定向搜索+LLM检查验证外部不可见的约束（如密码哈希、CI/CD配置）。
- **UI并行调度**：用LLM声明UI需求间的阻塞依赖，构建任务DAG，通过整数规划最小化makespan +重复设置，跨浏览器worker分区。
- **反馈生成**：输出条目级证据（观察到的UI状态、API响应、代码位置、失败的前提条件、受影响的权重），作为排序后的修复议程传回LegoGent。

### 6. 论文的主要结论与发现

- **拓扑与模型能力同样重要**：DeepSeek v4 Pro在即时通讯上从pipeline模式89.9分到open-source-review模式43.0分；全网格10模式平均，QA-first和Rotation并列最高（83.3），open-source-review最低（73.5）。
- **结构化流水线最优**：Pipeline模式以最高质量最快收敛（如P05电子商务96.2），因为其干净的工件边界和串行控制。
- **重管理监督有害**：PM oversight在某些项目领先（P00 83.7、P02 80.9），但整体开销大；过度编排会拖慢速度并降低质量。
- **成本前沿≠分数前沿**：GLM-5.2达到最高的全网格平均分但耗时和成本最高（约2.6倍墙钟时间、约8倍成本 vs DeepSeek v4 Pro）；Flash在34/100配置中令牌更多但更便宜（缓存读取便宜）。
- **QA-first擅长需求密集型项目**：将需求转化为验收目标，在P08（新闻搜索99.1）、P03（需求追踪91.7）、P04（AI图像修复78.4）最强。
- **Feature squad最均衡**：在5个项目上进入前三，尤其适合跨层交互链长的项目。
- **大修复增益可能隐藏弱首轮**：open-source-review和competitive模式R1→R3增益大，但得分或成本劣势表明增益来自弱首轮的追赶而非更优策略。
- **回归是独特的失败模式**：82.0%的轮次转换有改进，94.7%的R3高于R1；但修复可能打破其他功能（如DeepSeek v4 Pro的PM模式在R3修复个人资料编辑但使搜索/好友/消息等回归，分数从80.9降至66.0）。
- **失败分类学**：不完整逻辑/边界情况（32.2%）和缺失功能（23.8%）占56%的失败；认证/权限（11.9%）和前提级联（11.0%）反映多智能体特定问题——一个所有者破坏的契约静默归零另一所有者的正确工作。
- **部署工件是固定扣分项**：安全/传输检查（8.5%）在近80%的运行中出现，因为依赖XDeploy集成。

### 7. 优点：方法或实验设计的亮点

- **真实项目基础**：10个项目来自真实课程作业，规模大（2000+行Python），不易受LLM数据污染影响。
- **部署接地评估**：通过原生的GitLab CI/CD和SonarQube路径部署，通过真实UI/API/代码检查而非最终文本检查打分。
- **成本感知**：区分四类令牌字段（新输入/缓存写/缓存读/输出），能区分原始令牌量与实际预算压力。
- **迭代反馈而非一次性成功**：最多3轮，暴露收敛和回归行为。
- **控制变量严谨**：协作模式是唯一自变量，使拓扑可测量。
- **所有权与责任映射**：LegoGent的完成门控和工件验证使“团队停止说话”≠“团队完成”可观察。
- **可解释的反馈**：TAgent提供条目级证据而非仅标量分数，使修复优先化基于加权根因。
- **TAgent的UI调度算法**：用整数规划和DAG减少重复设置，是以“消除冗余设置”为导向的类多智能体并行。
- **完整资源开源**：项目规格、模式定义、源码、指标和分析脚本全部公开在GitHub。

### 8. 不足与局限

- **随机性与规模受限**：LLM随机性缓解有限（三重试验仅用于即时通讯项目），高测试预算限制更大规模实验。
- **任务范围偏窄**：仅覆盖Web应用，不覆盖灾难恢复、长期维护等软件生命周期其他阶段；TAgent可能漏掉一些外部不可见的边缘缺陷。
- **TAgent与TA分数相关性**：仅报告Spearman相关性0.87（学生项目），但未提供置信区间或更细致的验证。
- **硬件信息不完整**：未明确GPU型号/数量，仅提及CPU，影响精确复现。
- **全网格模型选择偏差**：Claude Opus 4.8和GPT-5.5仅跑单项目，跨项目泛化结论主要基于DeepSeek/GLM三家模型。
- **缓存定价依赖供应商**：缓存写/读价格因供应商而异，成本比较可能随定价变化而失效。
- **部署层CI/CD是固定扣分项**：安全/传输检查依赖XDeploy，这可能低估某些模型在部署方面的真实编码能力（因为代价固定而非模型可改）。
- **三轮回合截断**：可能截断了慢模型（如GLM-5.2）的尾部恢复潜力。
