## 摘要
大型语言模型已将人工智能从孤立的预测服务转变为长期运行的分布式系统的组成部分，这些系统能够推理、调用工具、检索外部状态、委派任务，并代表用户和组织采取行动。周边生态系统已通过智能体框架、工作流引擎、模型服务平台、记忆系统、通信协议和可观测性工具做出响应。这些技术改进了执行，但它们并未提供一个稳定的、独立于实现的操作架构来治理意图、选择能力、在委派中保持权威、控制不确定性、协调运行时行为，以及重构重大行动发生的原因。本文提出智能体操作系统（AOS），一种面向分布式智能体系统的供应商中立的参考操作架构。AOS包含两个内部平面：控制与治理平面，负责意图、策略、信任、权威、置信度、可审计性、可观测性和人类监督；运行时与协调平面，负责智能体生命周期、工作流协调、模型和工具路由、上下文与记忆协调、调度、流量管理和运行时保障。平台服务、Linux或Windows、容器运行时和物理基础设施保持在AOS边界之外，并通过显式接口集成。本文规定了AOS概念、不变量、接口对象、优化目标、部署配置文件和可靠性责任。它还指出了权衡和未解决的研究问题。AOS并非作为现有框架或基础设施的替代品；它被提议作为操作架构，通过该架构，异构组件可以被组合成可治理、可靠、可观测和可互操作的智能体系统。

## Abstract
Large language models have transformed artificial intelligence from isolated prediction services into components of long-running, distributed systems that reason, invoke tools, retrieve external state, delegate tasks, and act on behalf of users and organizations. The surrounding ecosystem has responded with agent frameworks, workflow engines, model-serving platforms, memory systems, communication protocols, and observability tools. These technologies improve execution, but they do not provide a stable, implementation-independent operating architecture for governing intent, selecting capabilities, preserving authority across delegation, controlling uncertainty, coordinating runtime behavior, and reconstructing why consequential actions occurred. This paper proposes the Agent Operating System (AOS), a vendor-neutral reference operating architecture for distributed agentic systems. AOS contains two internal planes: a Control & Governance Plane responsible for intent, policy, trust, authority, confidence, auditability, observability, and human oversight; and a Runtime & Coordination Plane responsible for agent lifecycle, workflow coordination, model and tool routing, context and memory coordination, scheduling, traffic management, and runtime assurance. Platform services, Linux or Windows, container runtimes, and physical infrastructure remain outside the AOS boundary and are integrated through explicit interfaces. The paper specifies AOS concepts, invariants, interface objects, optimization objectives, deployment profiles, and reliability responsibilities. It also identifies tradeoffs and unresolved research questions. AOS is not presented as a replacement for existing frameworks or infrastructure; it is proposed as the operating architecture through which heterogeneous components can be composed into governable, reliable, observable, and interoperable agentic systems.

## 1. 核心问题与研究动机

### 背景
- LLM的出现使AI从"孤立的预测服务"转变为"长期运行的分布式系统组件"——这些系统能够推理、调用工具、检索外部状态、委派任务并代表用户采取行动。
- 当前生态系统已涌现出智能体框架（AutoGen、LangGraph、CrewAI）、工作流引擎、模型服务平台、记忆系统、通信协议（MCP、A2A）和可观测性工具（OpenTelemetry）等。
- 但这些技术仅优化了**执行**，缺乏一个**稳定的、与实现无关的操作架构**，来统一治理：意图、能力选择、授权委派、不确定性控制、运行时协调和事后审计。

### 核心问题
论文提出的中心研究问题是：
> 需要一个什么样的独立于实现的操作架构，才能使分布式智能体系统在异构运行时、协议、平台、操作系统和基础设施独立演进的同时，保持可治理、可靠、可观测、可信和可互操作？

### 关键洞察
- 现有架构大多是"执行中心主义"的：智能体框架提供推理循环，Kubernetes调度容器，Linux控制进程——但没有一层负责**语义控制**。
- 例如，一个"调查失败部署"的请求，在规划层是人类可读的行动描述，在操作系统层是系统调用和资源访问。两者之间存在巨大的**语义鸿沟**，需要一个架构来跨越。
- 现有日志和追踪系统难以重构"在某个特定委派权限下发生了哪些操作"——这被称为委派归因问题。

## 2. 方法论与核心架构

### 总体思路
论文的答案是提出 **AOS（Agent Operating System，智能体操作系统）**——一个包含两个内部平面的参考操作架构。AOS不是要替代现有系统，而是提供一个坐标系，使异构组件能够被组合成可治理、可靠、可观测、可互操作的整体。

### AOS 边界
- **边界内部**：两个平面。
- **边界外部**：平台服务（模型端点、数据库、身份提供商、策略引擎等）、Linux/Windows操作系统、容器运行时、物理基础设施。它们通过显式接口被集成和管理。

### 两个平面

**① 控制与治理平面（Control & Governance Plane）**
- 回答"应该发生什么、在谁的授权下、受哪些约束限制"
- 职责包括：意图管理、能力发现、策略与信任评估、置信度与风险决策、委派治理、审计与可观测性义务、人类监督。
- 核心输出是**授权的执行指令（ExecutionDirective）**——一个包含策略决策、委派上下文、置信度阈值、执行约束和失败策略的"契约"。
- 关键不变量：**该平面不得断言工作已经发生或成功**；运行时证据是闭环的必要条件。

**② 运行时与协调平面（Runtime & Coordination Plane）**
- 回答"批准的工作应如何被协调和保障"
- 职责包括：智能体生命周期管理、工作流协调、模型/工具/API/人工路由、上下文与记忆协调、调度、流量管理、协议中介、运行时保障。
- 关键不变量：**该平面不得扩大权限、不得静默丢弃义务、不得在没有回到控制平面的情况下重新定义成功标准**。

### 核心抽象对象（Foundational Concepts）
| 对象 | 含义 |
|---|---|
| Intent（意图） | 最高层的目标描述 + 约束 + 权威 + 策略 + 上下文 + 成功标准 + 时间要求；不可变、提供者无关 |
| Context（上下文） | 为特定决策或执行步骤选择的有界操作状态；有范围、有出处、可审计 |
| Capability（能力） | 稳定的、可发现的结果契约（如 ai.case.summary.generate），将请求结果与可替换的实现（提供者）分离 |
| Provider（提供者） | 能力的具体实现（智能体、模型、工具、人类、工作流等）；可替换、独立版本化 |
| Plan（计划） | 将意图分解为步骤、依赖、检查点和失败操作；计划不等同于授权 |
| Policy（策略） | 机器可评估的规则，产生 allow/deny/modify/approve + 义务 的确定性决策 |
| Delegation（委派） | 有界的权威转移，保持父级血缘、约束和撤销语义；子级范围不得超过父级 |
| Trust（信任） | 针对特定意图和策略上下文的、基于证据的关系评估，而非通用声誉分数 |
| Confidence（置信度） | 多维度的操作保障信号（意图清晰度、上下文充分性、数据质量、模型校准等），驱动proceed/retry/fallback/escalate等控制动作 |
| Evidence / Provenance（证据与出处） | 用于证明和重建控制或执行决策的可观测工件集合 |

### 关键设计原则
1. **控制与执行分离**：决策记录、执行指令和观察到的动作必须是独立对象。
2. **能力中心主义**：请求方指定"要什么"而非"用哪个模型/工具"。
3. **权威保留与最小委派**：从根目标到最终副作用的权威链必须始终可见；子级只能收到完成委派工作所必需的最小范围。
4. **围绕概率推理的确定性执行边界**：访问受保护数据或修改外部状态的动作必须跨越确定性策略、模式和运行时强制边界。
5. **置信度作为控制信号**：置信度必须驱动具体行为（如低置信度金融转账不得继续，低置信度可逆摘要可带警告继续）。
6. **天然可观测性**：语义字段在系统运行时即被创建，而非事后从日志文本中重建。
7. **显式状态与合法转换**：意图、计划、委派、执行都有声明的生命周期状态和合法转换。
8. **运行时/模型/云/操作系统无关**：AOS定义语义责任和契约，而非专属实现。
9. **联邦而非全球单体**：各组织和区域保留本地策略、信任、数据和运行时控制，同时共享能力广告和可互操作的证据。
10. **可靠性是端到端属性**，由控制平面、运行时、平台服务、操作系统和人类操作共同产生。

### 数学建模（简要）
- **可行性先于优化**：硬约束（授权、策略、数据驻留、协议兼容性、最低信任等）构成可行集 F(i, S_t)；任何效用优化都不能覆盖硬约束失败。
- **多目标提供者选择**：效用函数 U(p|i) 综合语义适配度、信任、预期置信度、可靠性、局部性、延迟、成本、能源和拥塞，权重由意图和策略决定。
- **委派单调性**：Perm(d_child) ⊆ Perm(d_parent)、Scope(d_child) ⊆ Scope(d_parent)、预算和有效期均不超过父级剩余。
- **置信度聚合**：加权几何平均 C_agg = Π max(ε, c_j)^{α_j}，对弱组件给予更强惩罚；保留组件向量以避免单一聚合值隐藏弱点。
- **风险与控制动作**：Risk(a) = Pr(H|e,x,a) × Impact(H) × Exposure(a)；控制策略 π_control 将置信度、风险、可逆性、权威上下文映射到显式动作（PROCEED、PROCEED_WITH_WARNING、RETRY、FALLBACK、ESCALATE、TERMINATE）。

## 6. 主要结论与发现

1. **现有智能体生态系统缺少操作架构**：所有现有组件（框架、协议、平台、观测系统）各自解决局部问题，但没有一个定义端到端的分布式智能体操作模型。碎片化的根源是独立演进，而非任何单个组件的缺陷。
2. **AOS 提供两平面参考架构**：控制与治理平面（决定"应该发生什么"）+ 运行时与协调平面（决定"如何协调和保障"），二者通过显式指令、证据和反馈通信。逻辑分离而非物理分离，同一进程可以承载两个平面。
3. **能力中心抽象是核心**：稳定的能力名称将请求的结果与可替换的提供者解耦，允许按策略、信任、成本、延迟、位置等进行路由。
4. **权威保持的委派是安全性的基础**：委派必须遵循单调非扩展原则、保留血缘、支持撤销。传统追踪结构不足以重建委派范围内的执行（引用[4]）。
5. **置信度必须从仪表盘指标提升为控制信号**：置信度需要有证据支持、可操作、策略驱动，而非仅仅是模型概率。
6. **AOS 不是替代品**：平台服务、Linux/Windows、Kubernetes、MCP、A2A 等仍然存在并发挥着各自作用。AOS 的价值在于为这些组件提供"如何组合成一个可治理系统"的坐标系。
7. **架构的成功标准**：AOS-0001 的成功应通过它是否改善技术讨论、暴露缺失责任、支持可互操作的实现、使系统更可治理和可理解来判断。

## 7. 优点与亮点

1. **厂商中立的架构定位**：不绑定任何云、模型、框架或协议，追求"实现多元性"——多个符合要求的控制平面、运行时、注册表、策略引擎可以共存。这使得架构具有长久的参考价值。
2. **清晰的两平面职责划分**：控制与执行分离，决策状态和运行状态可独立演进、独立替换、协同追踪。这个边界定义比AIOS等单内核式提案更完整——端到端操作责任包含了从意图翻译到执行的整个过程。
3. **系统的对象模型**：意图→上下文→能力→提供者→计划→策略→委派→信任→置信度→证据，十个概念互相关联、不变量明确。为跨组件通信提供了语义基础。
4. **权威工程的前瞻性**：将委派范围单调性、血缘保持、撤销语义、委派归因问题作为一等公民，直接回应了分布式智能体系统的核心安全风险（混淆代理问题）。
5. **置信度建模的严谨性**：置信度是多维向量而非单个分数；保留组件证据；明确与风险的关系；映射到具体控制动作。避免了对模型概率的过度信任。
6. **与现有生态的兼容性**：MCP可实现工具访问适配器、A2A可实现智能体通信适配器、OpenTelemetry可作为语义事件的传输层。不要求替换现有系统，降低了采纳门槛。
7. **深度承认架构张力**：集中化vs联邦、强观测vs隐私、确定性边界vs延迟、全局发现vs主权控制——论文明确承认这些矛盾并提供了解决的策略对象。
8. **威胁模型的完整性**：附录D覆盖了意图操纵、注册表投毒、权限升级、策略绕过、上下文窃取、工具滥用、委派混淆、置信度欺骗、重试放大、审计篡改、内核逃逸、人工批准欺骗等12类威胁，控制措施与架构对象一一对应。
9. **规范的文档治理**：BCP 14规范语言、明确的贡献模型、版本化修订机制（ADR流程）、架构承诺清单，为长期系列规范的演化提供了治理基础。

## 8. 不足与局限

### 缺少实证验证
- 这是最重大的局限。论文是纯架构提案，没有实验数据、没有基准测试、没有案例研究来支撑核心主张。
- 没有任何证据表明"能力中心抽象确实能改善治理"或"置信度控制信号在实际系统中有效"。
- 论文提出的数学公式（如效用函数、置信度聚合）是"说明性的"，未经受真实负载检验。

### 语义互操作性被简化
- 论文承认：如果两个提供者都广告 ai.case.summary.generate 但对"case"或"cited"理解不同，发现将产生虚假的互操作性。
- 能力语义的标准化、域本体、协商协议都留待未来工作（AOS-0004），但这正是能力中心设计能否成立的关键问题。
- 论文提出的"能力"与安全领域传统的"capability"（不可伪造的授权令牌）含义不同，容易混淆；论文虽作了区分，但跨社区交流时仍有歧义。

### 对声明式元数据的依赖
- 论文自己也承认（第15.10节）：不变量依赖于验证过的能力元数据——一个动作是否"具有后果"取决于声明的副作用。如果提供者未声明其副作用，检测将落到运行时保障和低层执行，**高保障配置文件不能仅依赖声明**。这意味着恶意或粗心的提供者可能导致治理失效。

### 置信度聚合的未决问题
- 加权几何平均是"一种保守聚合"，但如何表示证据源之间的依赖关系、如何避免重复计算同一证据的信息、如何进行校准和不确定性区间估计，均留待AOS-0005。
- 论文没有解决"不同来源置信度分数不可直接比较"的问题——提供者自报的质量分与受信任的评估分是否可以在同一公式中混合使用。

### 联邦策略冲突与撤销一致性未解决
- 论文承认联邦策略冲突解决和撤销一致性是开放研究问题。在核心架构承诺中，联邦更多的还是"开放提案"而非已解决的设计。

### 安全与权威翻译的未决问题
- 论文承认最高难度的安全问题——从语义权威到具体执行约束的翻译——并未解决。"一个策略允许智能体'读取项目日志'，但操作系统需要路径、文件描述符、凭证、进程、套接字和系统调用。" 过度宽泛的翻译破坏最小权限；过度狭隘的翻译妨碍有用工作。

### 控制平面可能成为瓶颈
- 论文讨论了控制平面的延迟和成本问题，提出了快速路径方案（缓存授权租约、本地提供者排名），但缺乏实证表明这些优化在真实负载下的效果。

### 可操作性与实践落地
- 论文是"参考架构"而非"产品"，没有提供现成的软件。aos-core还处于演进中。
- 对期望采纳该架构的工程团队而言，从架构到实际部署之间仍有大量规范和工具需要补齐。

### 评估

### 评估

#### 综合价值定位
这是一篇典型的**参考架构（Reference Architecture）预印本**，其价值不在实证结果，而在系统化的概念框架。它试图回答一个当前领域尚无人完整回答的问题：当智能体成为分布式系统中的一等公民时，操作系统层应提供什么样的抽象与不变量？在这个意义上，论文的贡献是**填补空白**而非**验证假设**。

从学术定位看，它类似于计算机网络早期的 OSI 模型或分布式系统中的 CORBA 参考架构——这类工作往往不是通过实验来证明自身，而是通过提供一种**统一的语言和坐标系**，使后续研究和工程实践能够在同一框架下对话。论文在这一点上是成功的：它给出了十个相互关联的核心抽象、两平面划分、12 类威胁模型和清晰的委派不变量，足以支撑后续研究者以此为基点展开工作。

#### 对领域的关键贡献
论文最重要的贡献，在于把"权威与委派"从安全技术的边缘议题提升为分布式智能体架构的**核心设计维度**。传统智能体框架关注推理和工具调用，传统平台关注调度和生命周期，而 AOS 明确地将"谁在什么授权下以什么约束做了什么"作为架构的中心问题。这一视角的转换很可能影响未来智能体平台的设计方向——正如 Kubernetes 将"声明式期望状态"引入容器编排，AOS 试图将"授权执行指令 + 证据回环"引入智能体操作。

第二个重要贡献是**置信度的操作化**。将置信度从模型输出的概率分数提升为多维度的、可驱动控制动作的信号，并连接风险与可逆性，这一思路对高保障场景（金融、医疗、政务）尤为关键。即使实现细节尚未完善，其方向性价值是明确的。

第三个贡献是**对现有生态的尊重**。论文反复强调 AOS 不是替代品，而是"坐标系"。这种务实的姿态，使架构建议具有现实可采纳性：工程团队可以在保留现有框架和协议的同时，逐步引入 AOS 的语义分层，而不必推翻既有系统。

#### 适用场景与目标读者
- **架构师与平台设计者**：在设计企业级智能体编排平台时，AOS 的对象模型和不变量可直接作为需求分析框架。
- **智能体框架维护者**：可用 AOS 的能力/提供者分层审视现有框架是否混淆了"意图"与"实现"。
- **政策与治理研究者**：第 8 章策略模型与附录 D 威胁模型为 AI 治理提供了可工程化的映射。
- **联邦与多租户系统开发者**：委派单调性、联邦边界与撤销问题提供了具体的协同设计参考。

#### 改进建议与未来方向
若论文希望从"参考架构"升格为"实际标准"，至少在以下方面需要补充：
1. **最小可验证实现（MVP）** ：将 aos-core 扩展为一个可部署的最小系统，并公开其接口契约。
2. **案例研究**：选择 2-3 个典型场景（如金融交易审批链、多机构联合调查、个人助手跨应用操作），展示 AOS 如何落地，即使只是定性分析。
3. **语义互操作实验**：设计一个小型能力注册表，测试不同提供者对同一能力名称的语义偏差在多大程度上影响路由正确性。
4. **性能表征**：测量控制平面在快速路径与完整评估路径下的延迟开销、吞吐和失败率。
5. **与现有标准互操作的实际测试**：实现 MCP/A2A/OpenTelemetry 适配器，展示端到端的可观测性和跨协议委派。

#### 总体评价
尽管缺乏实证，论文在**概念完整性、工程可理解性和前瞻性**上均属上乘。它的行文风格接近 IETF 与 W3C 的规范文档，语言严谨、边界清晰、不夸大结论。对于关注分布式智能体系统理论基础和架构设计的读者，这是一篇值得精读并可能引为框架性参考的论文；对于希望获得现成可运行系统的读者，则需等待后续工作。

**一句话总结**：AOS 是一份具有标准潜质的智能体操作参考架构提案，它的价值在于为"可治理的分布式智能体"提供了一个清晰、兼容、可讨论的共同框架，但其有效性仍有待实证检验。
