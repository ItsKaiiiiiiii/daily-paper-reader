## 摘要
编码代理已迅速成为AI辅助软件开发的主要界面。然而，尽管其采用率不断增长，但对其内部架构的了解相对较少，目前尚无类似于编译器或操作系统那样系统的架构描述。本文通过记录编码代理的主要架构组件、解释其职责、交互和执行流程来填补这一空白。为支持这项工作，我们还介绍了Ark（Agent Research Kit），一个为研究和教育设计的最小开源编码代理，它保留了现代编码代理的基本架构机制，同时强调简单性和清晰性。我们还引入了ArkBench，一个包含十项代表性软件维护和演化任务的轻量级基准。使用gpt-5.4-mini，Ark成功解决了10个任务中的8个，同时消耗了适度的token。最后，我们使用最近提出的架构分类法将Ark的架构与最先进的编码代理进行了比较。我们希望Ark和ArkBench能为编码代理的教学、研究和实验提供实用的基础。

## Abstract
Coding agents have rapidly emerged as the primary interface for AI-assisted software development. However, despite their growing adoption, relatively little is known about their internal architecture, and no systematic architectural description comparable to those available for compilers or operating systems currently exists. This paper addresses this gap by documenting the main architectural components of coding agents, explaining their responsibilities, interactions, and execution flow. To support this effort, we also present Ark (Agent Research Kit), a minimal open-source coding agent designed for research and education that preserves the essential architectural mechanisms of modern coding agents while emphasizing simplicity and clarity. We also introduce ArkBench, a lightweight benchmark comprising ten representative software maintenance and evolution tasks. Using gpt-5.4-mini, Ark successfully solved 8 of the 10 tasks while requiring modest token consumption. Finally, we compare the architecture of Ark with those of state-of-the-art coding agents using a recently proposed architectural taxonomy. We hope that both Ark and ArkBench provide a practical foundation for teaching, research, and experimentation on coding agents.

## 1. 核心问题与研究动机

- **背景**：编码代理（Coding Agents）已成为 AI 辅助软件开发的主要界面，能够自主完成代码检查、信息搜索、测试运行、文件编辑等完整开发任务，并正被快速集成到开发者工作流中。
- **核心问题**：尽管编码代理采用率极高，但其内部架构缺乏系统化的描述。商业系统（如 Claude Code、Cursor）不公开实现，开源系统（如 Codex、OpenCode、Aider）代码复杂且文档以安装使用为主，难以理解其架构原理。目前不存在类似编译器或操作系统那样成熟的架构参考文档。
- **研究意义**：编码代理正在成为软件开发的主要接口，如同 1970 年代高级语言兴起时的编译器；但架构知识的缺失阻碍了教学、研究、复用和进一步创新。本文旨在填补这一空白，提供清晰的架构蓝本。

## 2. 方法论

- **核心思想**：通过实现一个极简、开源、面向研究与教育的编码代理 Ark（Agent Research Kit），以“做中学”的方式揭示编码代理的核心架构，并配套轻量级基准 ArkBench 进行验证。
- **关键技术细节**：
  - **架构组件**：系统化描述了九个核心组件——Agentic Loop（代理循环）、System Prompt（系统提示）、Tools（工具）、Memory（记忆）、Context（上下文）、Error Handling（错误处理）、Security Mechanisms（安全机制）、Tracing（追踪）、LLM Integration（LLM 集成）。
  - **Agentic Loop**：采用 ReAct（Reason + Act）范式，LLM 交替进行推理和工具调用，直至任务完成。Ark 的循环实现仅 18 行代码，核心逻辑为：创建记忆 → 调用 LLM 获取下一动作 → 若为 finish 则处理补丁并结束；否则执行工具、记录结果、继续迭代。
  - **系统提示词**：33 行，定义角色、ReAct 协议格式、工具列表、操作约束（如必须先读文件才能修改）、终止条件（最终输出 unified diff patch）等。
  - **工具集**：仅 5 个工具——list_files、read_file、find_text、run_tests、finish，直接以 Python 实现，简化集成。
  - **记忆与上下文**：记忆记录每轮工具请求与结果；上下文包含任务描述、AGENTS.md 工作区指令、自动生成的状态摘要、最近 4 轮交互历史（用于控制 token 消耗）。
  - **错误处理**：对不符合 ReAct 协议的 LLM 响应进行一次性修复尝试；对补丁进行校验，自动修正 hunk 行数错误等小问题，使用 `git apply --check` 验证。
  - **安全机制**：临时工作区隔离（复制项目到 ark-workspace）、路径限制、固定测试命令（pytest）、补丁验证与用户批准。
  - **实现规模**：13 个 Python 源文件，共 1471 行代码，50 个单元测试，仅两个外部依赖（openai、pytest）。
  - **开发过程**：采用迭代式开发，初始参考 ReAct 论文、OpenAI Codex 和 Anthropic Claude Code 文档；开发过程中使用 Codex 辅助生成代码，37% 的提交用于重构，32% 用于文档改进。

## 3. 实验设计

- **基准**：ArkBench——一个轻量级编码代理基准，基于小型过程式电子商务应用（Python 实现），包含 10 个独立维护任务，分为三类：
  - 3 个 Bug 修复（如目录分页 off-by-one、订单校验缺失、折扣阈值计算错误）
  - 3 个重构（如提取公共函数、移动格式化函数、重命名公共函数并更新调用）
  - 4 个功能实现（如按价格区间过滤、按价格排序、CSV 导出、按类别分组）
- **任务结构**：每个任务有独立项目副本，包含 prompt.txt（任务描述，不指明修改文件）、tests（公开测试）、evaluation（隐藏测试和结构化检查脚本）。
- **评估指标**：任务成功率（成功/失败）、token 消耗、执行时间、工具调用次数。
- **对比方法**：
  - 不直接与 SOTA 代理对比性能（作者明确说明这不是主要目标），而是使用 Rombaut 提出的架构分类法，将 Ark 与 Codex CLI 和 OpenCode 三个层面（控制架构、工具与环境接口、资源管理）进行定性架构对比。

- **充分性与客观性**：
  - **优点**：任务覆盖三种常见维护类型，且包含隐藏测试和结构化检查，能较好反映真实开发场景；成本低、可复现性较好。

## 6. 主要结论与发现

- **架构清晰性**：Ark 验证了编码代理的架构可以在极简实现中保持核心机制——ReAct 循环、LLM 驱动、工具调用、记忆和上下文管理，总计仅约 1470 行代码。
- **可行性**：Ark 在 ArkBench 上成功解决 8/10 任务（80%），平均执行时间 23.5 秒/任务，平均 token 消耗 3,342，平均工具调用 7.1 次，成本低于 0.5 美元。
- **失败案例分析**：
  - bugfix-02 失败：修复不完整，只处理了可见测试覆盖的非法输入，遗漏了 customer 对象缺少 id 字段时的异常类型错误（KeyError 而非 ValueError）。
  - refactor-03 失败：补丁应用成功但重命名未传播到所有导入和调用点，导致收集测试时 import 错误——这是 LLM 代理在重构任务中的常见局限（主变换正确但遗漏次要依赖）。
- **架构对比结论**：Ark 与 Codex CLI、OpenCode 在控制架构上完全一致（ReAct 循环、LLM 驱动、命令式 while 循环实现）；主要差异在工具集规模（5 vs 20+）、上下文压缩策略（截断 vs LLM 摘要）、持久记忆（无 vs 有）、多模型路由（无 vs 有）。这些简化使 Ark 更易理解、修改和扩展。

## 7. 优点

- **填补空白**：首次以系统化、教学友好的方式记录了编码代理的架构组件和交互流程，类比编译器架构文档，具有较高的学术参考价值。
- **设计优雅**：极简实现（约 1500 行 Python）却覆盖了编码代理的关键机制，代码清晰、模块化好（37% 提交用于重构），易读易扩展。
- **开源友好**：Ark 和 ArkBench 均在 MIT 许可下开源，附带完整文档、测试和 100% 行覆盖率，为后续研究者提供了可直接试用的实验平台。
- **成本极低**：整个基准评估成本不到 0.5 美元，使教学和研究不需要昂贵算力即可开展。
- **实践驱动**：开发过程本身使用了另一个编码代理（Codex），体现了“用代理构建代理”的实践性；失败案例的深入分析也为读者提供了有价值的经验。

## 8. 不足与局限

- **实验规模有限**：ArkBench 仅 10 个任务，且为简单的过程式 Python 项目，未涉及复杂依赖、大型代码库、多语言或真实 GitHub issue，泛化性存疑。
- **缺乏统计稳健性**：每个任务只执行一次，未报告多次运行的平均值与方差，LLM 的非确定性可能导致结果偏差；缺少消融实验（如不同上下文窗口、不同工具集的影响）。
- **无性能对比基准**：未与其他编码代理在相同任务上对比，无法证明 Ark 的竞争力，仅证明“能用”。
- **模型依赖单一**：仅使用 gpt-5.4-mini，模型性能对结果影响很大（早前本地模型表现不佳），不能代表所有 LLM 下 Ark 的行为。
- **功能简化带来的局限**：无持久记忆、无会话恢复、上下文仅保留最近 4 轮、搜索仅支持关键字（不支持正则）、工具集过小，在处理复杂任务时可能明显不足。
- **安全性依赖用户批准**：虽然具有临时隔离和路径限制，但最终补丁应用仍需用户手动批准，自动化程度有限；也未涉及沙箱等更高级的安全隔离。
- **研究时效性**：论文发布时间为 2026 年，引用的模型（gpt-5.4-mini、ChatGPT 5.5）和系统版本（Codex CLI、OpenCode）可能迅速演进，结论可能短期内过时。
