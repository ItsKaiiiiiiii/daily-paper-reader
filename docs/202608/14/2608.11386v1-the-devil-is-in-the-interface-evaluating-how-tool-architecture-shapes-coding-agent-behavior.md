## 摘要
随着大型语言模型的持续改进，代理系统变得日益重要，而工具是一个关键的设计维度，因为它们决定了代理如何获取信息并在其环境中采取行动。先前关于代理工具的研究主要集中于扩展代理的能力，但对于这些能力如何被组织并暴露给模型，关注较少。我们将后一个设计维度称为工具架构。我们通过在仓库级问题修复上的受控实验研究编码代理中的工具架构，比较了六种工具架构，这些架构在底层信息和行动相似的情况下，改变了它们向模型的组织与暴露方式，涉及三个主体角色，共11,700条轨迹。实验表明，即使工具提供相似的能力，工具架构也会改变代理的行为：与代理仅拥有bash工具的基础架构相比，更结构化的底层接口将重复尝试间的一致性提升了多达4.7倍；自然语言搜索拓宽了仓库探索范围，使对相关文件的访问增加了超过11%；Python CodeAct风格的接口以41.6%更少的步骤和56.3%更低的令牌使用量实现了相似的任务性能。相比之下，轻量级的基于文本的认知脚手架工具（例如允许代理记录中间推理的工具）对主体行为的影响有限。

## Abstract
As large language models continue to improve, agentic systems are becoming increasingly important, and tools are a key design dimension because they determine how agents access information and take action in their environments. Prior work on agent tooling has primarily focused on expanding what agents can do, but has paid less systematic attention to how those capabilities are organized and exposed to the model. We refer to this latter design dimension as tool architecture. We study tool architecture in coding agents through controlled experiments on repository-level issue fixing, comparing six tool architectures that hold the underlying information and actions similar while varying how they are organized and exposed to the model, across three actors and a total of 11,700 trajectories. Our experiments show that, even when tools provide similar capabilities, tool architecture changes agent behavior: Compared to a basic architecture where the agent has only the bash tool, more structured low-level interfaces improve consistency across repeated attempts by up to 4.7 $\times$; natural-language search broadens repository exploration and increases access to relevant files by more than 11%; and Python CodeAct-style interfaces achieve similar task performance with 41.6% fewer steps and 56.3% lower token usage. By contrast, lightweight text-based cognitive-scaffolding tools, such as tools that let the agent record intermediate reasoning, have limited effect on actor behavior.

  - **工具能力（Tool Capability）**：代理可使用的信息和动作集合，类比于软件工程中的“功能”；
  - **工具架构（Tool Architecture）**：这些能力如何被组织、抽象和暴露给模型，类比于软件工程中的“软件架构/接口设计”。
- **核心问题**：当两个代理能够访问相似的信息并执行相似的动作时，仅仅改变这些能力的组织与暴露方式（即工具架构），是否会显著改变代理行为？

## 2. 方法论：核心思想与技术细节

### 2.1 总体思路

通过受控实验，在**保持工具能力相似**的前提下，系统比较六种不同的工具架构，从而将“架构效应”与“能力效应”分离开来。

### 2.2 六种工具架构设计

文章沿两个维度构建了六种架构，**以 BashOnly 为基线**：

| 维度 | 架构 | 核心设计 |
|------|------|---------|
| 基线 | **BashOnly** | 代理仅通过通用 shell 与仓库交互，自由组合底层命令完成导航、搜索、编辑、执行等 |
| 抽象层次 | **Atomic** | 将高频局部操作封装为显式工具（搜索、有界文件查看、定向替换、创建文件），能力不超出 bash（附录表3给出了原子工具与 bash 的等价映射） |
| 抽象层次 | **NLSearch** | 提供自然语言搜索接口，接收 NL 查询并返回相关代码片段；实现上不用语义索引/嵌入检索，而是用**同型号子代理 + bash（grep/find）**迭代搜索，确保不超越 bash 能力 |
| 抽象层次 | **Python** | 用可执行 Python 代码块替代逐一工具调用（CodeAct 风格），代理通过写 Python 遍历仓库、检查文件、编辑和执行测试 |
| 认知脚手架 | **HypoTrack** | 增加记录/更新假设及其置信度的工具，仅记录文本状态，不增加检索、记忆管理等额外能力 |
| 认知脚手架 | **Scratchpad** | 增加自由形式的"草稿本"工具，接受自由文本并返回确认，不超越模型原有推理文本能力 |

### 2.3 能力等价的验证

- 对 Python 架构：人工抽查 100 个 Python 动作，**97%** 对应 BashOnly 中已有的操作；
- 对 Atomic：附录表3直接给出每个原子工具与 bash 命令的等价映射；
- 对认知脚手架：工具只提供文本记录通道，不增加信息/检索策略或新的推理策略。

### 2.4 评估维度与指标定义

四个方面、五个核心指标：

1. **任务解析率（Resolve Rate）**：`ResolveRate(i,s) = c(i,s)/n`，单次尝试成功的概率；
2. **一致性（Consistency）**：`pass^k`，即同一问题实例的 k 次重复尝试**全部成功**的概率，`pass^k(i,s) = C(c(i,s), k) / C(n, k)`，k∈{5,7,9}；
3. **探索性——文件读取多样性**：重复尝试间读取文件集合的**Jaccard 距离**；
4. **探索性——解决方案多样性**：生成补丁之间的**CodeBLEU 距离**；
5. **效率（Efficiency）**：轨迹长度（交互步数）、输入 token 总数（跨 API 调用累积）、输出 token 总数、观测 token 总数。

### 2.5 关键分析机制

- **Atomic 一致性机制**：基于软件可靠性中的"故障—错误—失败"链，分析环境交互错误（分为**错位参数**、**错误编辑**、**语法错误**三类），验证 Atomic 通过减少低层交互错误提升一致性；
- **NLSearch 探索机制**：比较前 20 步的搜索动作多样性（Jaccard 距离与归一化 Levenshtein 距离），并用"高相关文件"代理指标（被所有架构的至少 3 条成功轨迹读取的文件）配合人工标注验证召回/精确率。

## 6. 主要结论与发现

### 发现 1：Atomic 提升一致性

- 相比 BashOnly，Atomic 对三个 actor 的 pass⁵/pass⁷/pass⁹ **全部为正增益**，是唯一具有跨 actor 一致正效应的架构；
- 对最弱模型 Qwen3Coder-30B 增益最大（+0.059~+0.074），对 Kimi（+0.013~+0.014）和 Sonnet（+0.017~+0.031）较小但稳定；30 次 rollout 的扩展实验确认增益保持稳定；
- **机制**：Atomic 显著减少低层环境交互错误（尤其是错误编辑和语法错误），弱模型受益最大。

### 发现 2：NLSearch 提升探索性但不提升方案多样性

- NLSearch 是唯一在三个 actor 上**一致增加文件读取多样性**的架构（Q3C +18.6%、Kimi +21.3%、Sonnet +13.4%）；
- 额外探索**确实有实际价值**：高相关文件召回率提升超过 11%，但精确率下降（NLSearch 精度 -0.046~-0.104）；
- 原因是自然语言查询比 grep/find 模式在重复尝试中**更多样化**；
- 但方案多样性（CodeBLEU 距离）变化很小，说明探索差异并未转化为最终补丁的策略差异。

### 发现 3：Python 效率最高

- 相比 BashOnly，Python 以 **41.6% 更少步骤**和 **56.3% 更低 token 消耗**实现相似任务性能；
- 效率提升主要来自**复合交互**：单条 Python 块内完成多项操作，大幅减少 API 调用次数；
- 对 Sonnet-4.5 还额外减少了"投机性重写"（反复全文件改写未执行验证）带来的浪费；
- Atomic 的效率效应依赖 actor 原有的交互粒度：接近原子操作风格的 Qwen 更高效（-32% 输入 token），而偏好复合操作的 Kimi 和 Sonnet 则增加开销（+20%）。

### 发现 4：轻量认知脚手架影响有限

- Scratchpad 的内容与 BashOnly 下模型已有推理高度相似（BLEU 普遍高于 0.6），未激发实质性新推理；
- HypoTrack 很少诱导真正的多分支假设推理，多数轨迹仅使用单线程假设甚至完全不用；
- 原因在于这些工具"不增加检索、记忆管理、新任务信息，也不强制推理策略"，因此模型只是将原有推理投影到新接口上。

### 泛化验证结论

- Atomic 提升 pass⁵（Q3C +9.5pp、Kimi +2.5pp 整体）、NLSearch 提升读取多样性（+13.0%、+9.4%）、Python 降低输入 token（-0.6M、-0.4M）和轨迹长度（-25.9、-15.1 步），方向与主实验一致。

### 总结论

- **工具架构本身即是一个关键设计维度**，在能力相似的条件下仍显著影响一致性、探索性与效率；
- 认知脚手架工具的轻量实现影响有限，但作者谨慎地将结论限定在"轻量文本型脚手架"，而非认知脚手架的普遍否定。

## 7. 优点与亮点

1. **概念框架清晰**：将工具设计拆分为"能力"与"架构"两个维度，借用软件工程中功能/架构的类比，做出了系统性的理论贡献；
2. **实验控制严谨**：六种架构均验证能力不超出 bash 基线，实现了难得的"变量隔离"，解决了既有研究中能力与架构纠缠导致归因不清的问题；
3. **评估维度丰富**：不只关心最终成功率，还系统量化了一致性（pass^k）、探索性（读取/方案多样性）、效率（步数/token），提供了代理非功能属性的全景视角；
4. **重复 rollout 设计**：10 次（部分 30 次）重复轨迹使一致性评估成为可能，这在同类研究中较为少见；
5. **机制分析深入**：从错误分类到搜索查询多样性，从 BLEU 相似度到人工标注验证代理指标，每个发现都有配套机制解释而非停留在统计关联；
6. **谨慎的结论边界**：对认知脚手架工具的负面结论明确限定在"轻量文本型"范围内，方法论上值得借鉴；
7. **泛化验证完备**：除主基准外，还覆盖了功能实现、调试等多种任务类型，增强了结论的外部效度。

## 8. 不足与局限

### 实验覆盖方面

- 基准子集仅采样了 SWE-bench Live 的 25 个仓库/65 个实例，规模有限；
- 泛化实验仅用开源模型、每组合仅 5 次 rollout，且是选择性配对比较，统计效力弱于主实验；
- 仅考察了仓库级 bug 修复类任务，未覆盖更广泛的多轮交互、长时任务或非编码代理场景。

### 偏差风险

- **NLSearch 的子代理实现**可能引入额外的隐式推理成本或不同行为，不完全等同于"纯接口差异"；
- 高相关文件的代理指标虽经人工验证（94.4% 精确率、97.6% 召回率），但文件"有用性"本身高度依赖轨迹上下文，代理指标仍可能简化了真实情况；
- 未报告置信区间或统计显著性检验，数值差异（如 Kimi 的 +0.013~+0.016）是否具备统计意义难以判断；
- Actor 模型的选取上，三个模型差异较大，可能在学习策略差异与工具架构效应之间存在混淆。

### 应用限制

- 轻量认知脚手架结论不能推广到更复杂的认知工具（如带检索增强的推理系统、MCTS 式规划）；
- Atomic 的效率效应高度依赖 actor 的自然交互风格，实际部署中选择工具架构需要针对具体模型调优，不能一概而论；
- 实验中的 Python 架构尚未引入真正的"新能力"（如更多库支持），因此结论不适用于 CodeAct 工具集本身带来的额外功能增益场景。

### 资源与复现

- 论文未披露算力配置，且 11,700 条轨迹的评估成本相当高，可能限制其他研究者的复现能力。
