## 摘要
执行框架设计通过塑造大型语言模型（LLM）在可执行环境中的感知、推理和行动方式，对智能体性能起着关键作用。最近的工作提出了自动执行框架演化，即从智能体与环境交互中迭代改进执行框架。然而，现有方法常常过拟合于演化任务，完全依赖轨迹推导信号，并联合优化执行框架组件，导致组件间干扰。我们提出HarnessCompass，一种围绕受限演化、主动反馈和组件级优化的新型自动执行框架演化框架。HarnessCompass首先对演化施加全局约束，将修改限制在与任务无关的执行框架变化上，这些变化能够泛化到演化任务之外。然后，它利用来自智能体关于执行框架使用的主动第一人称反馈来增强轨迹推导证据，为演化提供更丰富的信号。最后，它将不同执行框架组件的优化解耦，然后将它们整合为统一的执行框架，在降低跨组件干扰的同时保持组件协同。在SWE-bench Verified上使用GPT-5.4，HarnessCompass在仅5次演化迭代中将Pass@1从54%提高到66%，在有效性和演化效率方面均优于AHE。此外，演化后的执行框架能有效迁移到保留任务和其他模型上，展现出比先前自动执行框架演化方法明显更强的泛化能力。

## Abstract
Harness design plays a critical role in agent performance by shaping how large language models (LLMs) perceive, reason over, and act within executable environments. Recent work has proposed automatic harness evolution, which iteratively improves the harness from agent--environment interactions. However, existing methods often overfit to the evolution tasks, rely exclusively on trajectory-derived signals, and optimize harness components jointly, causing interference across components. We propose HarnessCompass, a novel automatic harness evolution framework built around constrained evolution, proactive feedback, and component-wise optimization. HarnessCompass first enforces global constraints on evolution, restricting modifications to task-agnostic harness changes that generalize beyond the evolution tasks. It then augments trajectory-derived evidence with proactive first-person feedback from the agent about harness usage, yielding richer signals for evolution. Finally, it decouples the optimization of different harness components before consolidating them into a unified harness, reducing cross-component interference while preserving component synergy. On SWE-bench Verified with GPT-5.4, HarnessCompass improves Pass@1 from 54\% to 66\% in only 5 evolution iterations, outperforming AHE in both effectiveness and evolution efficiency. In addition, the evolved harness transfers effectively to held-out tasks and other models, demonstrating substantially stronger generalization than prior automatic harness evolution methods.

## 1. 核心问题与研究动机

- **研究背景**：LLM 智能体在可执行环境中的性能不仅取决于基础模型本身，还高度依赖 **harness（执行框架）**——即协调模型与环境交互的软件层，包括提示词、工具、中间件、记忆和验证例程等。研究发现，仅改进 harness 设计即可在基础模型固定时大幅改变智能体性能。

- **现有瓶颈**：最优 harness 与具体模型强相关，每当基础模型更换就需要重新调优。传统做法依赖开发者手工分析轨迹、诊断失败并修订 harness，无法跟上模型快速迭代的步伐，因此催生了**自动执行框架演化（automatic harness evolution）**——由元智能体基于智能体-环境交互迭代改进 harness。

- **现有方法的三大局限**：
  1. **过度拟合搜索任务**：元智能体可自由修改 harness 并针对固定任务集的验证器反馈进行优化，倾向于编码任务特定的捷径，提升搜索集分数但无法迁移到保留任务。
  2. **仅依赖轨迹信号**：元智能体只能从外部观察智能体交互，知道任务失败及其位置，却无法了解智能体为何觉得 harness 难用，容易产生错误归因（如将 harness 摩擦误判为智能体错误，或将推理失败误归咎于缺少工具）。
  3. **联合优化所有组件**：提示词、工具、中间件、记忆等在同一轮中同时修改，编辑之间相互干扰，各编辑单独带来的增益无法叠加。

- **核心主张**：问题的根源不在于 harness 演化本身，而在于**演化过程缺乏结构与纪律**。有效的 harness 应来自一个有纪律的演化过程——约束可修改内容、提供更丰富的推理证据、在整合前隔离单个修改。


## 2. 方法论

### 2.1 总体框架

HarnessCompass 采用迭代闭环，每轮包含三个阶段：在搜索任务上评估当前 harness → 分析轨迹 → 基于分析改进 harness。核心创新在于用三大原则规范这一循环。

**预置定义**：基础模型 M 固定不变；harness H 表示为七类可编辑组件，分为两类——结构组件（工具实现、中间件、子智能体配置）与引导组件（系统提示词、工具描述、技能、长期记忆）。使用验证器对每条轨迹判定二值结果，Pass@1 为平均成功率。初始 harness 被故意设置为极简（仅有单一 shell 命令工具和简短系统提示词），确保后续的每个组件都由演化循环自身引入和度量。

### 2.2 三大核心原则

#### ① 受限演化（Constrained Evolution）

通过**全局泛化门控（generalization gate）** 对抗过拟合，每个候选编辑必须通过两道关卡：

- **内容约束**：拒绝任何提及具体任务实例、测试函数、私有符号的编辑，禁止基于特定任务 token 的代码分支。只允许携带**可评估的适用条件**的可复用决策准则——即"可迁移的设计原则"。
- **放置约束**：将编辑分为两类——
  - **能力类编辑**（新增可执行功能，如运行测试、安装缺失包）必须实现为中间件/工具/子智能体中的可执行代码；
  - **引导类编辑**（仅提供行为指令）必须放在系统提示词或记忆中，禁止将引导编码为可执行逻辑。

#### ② 主动反馈（Proactive Feedback）

补充轨迹无法提供的第一人称信号，分三步实现：

- **引导第一人称反馈**：对每个失败任务，使用同一基础模型 M 提出两类查询——
  - **盲目报告（blind report）** ：不透露验证结果，让智能体报告 harness 在何处阻碍执行、希望拥有什么能力，避免事后偏差；
  - **事后报告（hindsight report）** ：透露验证结果，让智能体将失败归因于四种原因（harness、智能体自身推理、任务歧义、环境），隔离 harness 相关问题。
- **轨迹接地（grounding）** ：反馈仅作为候选证据，必须得到轨迹支持才保留——对现有组件的抱怨需轨迹直接显示困难；对新能力的请求需轨迹展示该能力能解决的具体缺口。未获支持的反馈被丢弃。
- **聚合使用**：按涉及的 harness 组件分组，基于报告一致性、受影响任务数、盲目/事后报告一致性计算置信度，作为补充证据（而非替代）提供给元智能体。

#### ③ 组件级优化（Component-wise Optimization）

该原则的核心在于先独立优化再统一整合，避免组件间干扰:

- **独立运行轨道**：每轮并行演化两个变体，结构变体仅修改结构组件，引导变体仅修改引导组件。两变体编辑互不相交的文件，因此互不干扰。评估后以 Pass@1 更高者为胜者。
- **R³ 整合**：以胜者为基座，对败者的编辑进行三步处理——
  1. **修正（Revision）** ：逐一审查败者的每个编辑，仅保留独立有益且与胜者不重复、不冲突者；
  2. **重组（Recombination）** ：将保留的编辑应用到胜者基座上，文件级冲突时胜者优先；
  3. **精简（Refinement）** ：删除虽不冲突但功能重叠的冗余编辑，保留更可靠组件对应的修改。

### 2.3 算法流程（伪代码逻辑）

- 初始化 `H⋆ = H0`
- 迭代 t = 1 到 N：
  1. 用当前 H⋆ 在搜索任务 D 上做 k 次 rollout，得到轨迹集 T；
  2. 从 T 蒸馏轨迹证据 E；
  3. 引导第一人称反馈并经轨迹接地，生成主动反馈 F；
  4. 对结构、引导两个轨道分别执行受限演化生成变体 Hc，各自评估 Pass@1；
  5. 选出胜者 w 与败者 ℓ；
  6. 通过 R³ 将败者的有用编辑整合到胜者基座上，得到整合 harness Ht；
  7. 只有当 Ht 优于当前 H⋆ 时才接受，否则保留原 Harness。

## 6. 主要结论与发现

1. **主结果领先**：在 SWE-bench Verified 上，HarnessCompass 将 Pass@1 从种子 54.0% 提升至 66.0%，仅用 5 轮演化，优于 AHE 的 63.0%（20 轮）；在 450 个保留任务上以 60.4% 大幅超越 AHE 的 54.7%，总分为 61.0% vs. AHE 的 55.5%。

2. **泛化优势突出**：HarnessCompass 在保留集上的优势（+5.7 点）大于演化集（+3.0 点），说明其改进真正可迁移，而非过拟合演化任务。

3. **跨模型迁移有效**：冻结的 harness 使 Claude-Sonnet-4.6 总分从 70.0% 提升至 73.8%，证明学到的是可复用的工程改进而非模型特定修复。

4. **三大原则互补**：泛化门控促进迁移，主动反馈扩展优化信号，R³ 整合恢复泛化并提升效率（轮数从 12 降至 5）。

5. **收益分布广泛**：收益集中在大型、对 harness 敏感的仓库（sphinx-doc 从 35.2% 到 58.0%，pytest 从 52.6% 到 68.4%，django 从 59.3% 到 70.1%），而在种子 harness 已强的仓库（如 scikit-learn）几乎不变。

6. **机制解释明确**：无门控演化的记忆是任务特定"答案书"（如"django__django-13158 应如何修改"），有门控演化则沉淀为带适用条件的跨任务决策准则——前者是记忆，后者才是知识。


## 7. 方法亮点与优点

1. **问题诊断精准**：将现有方法的问题归纳为"过度自由的编辑 + 结果导向的证据 + 同步全改"三位一体的根源性缺陷，分析框架清晰且具有普适性。

2. **"纪律性演化"理念新颖**：强调演化过程的结构与纪律比搜索本身更重要，为自动 harness 演化领域提供了新的设计哲学。

3. **三大原则环环相扣**：受限演化（约束改什么）、主动反馈（丰富证据来源）、组件级优化（隔离干扰再整合）分别对应三大局限，逻辑自洽、覆盖完整。

4. **盲/事后双重反馈机制巧妙**：通过"不知结果"与"已知结果"的对照，减少事后合理化偏差，同时用轨迹接地过滤虚假归因，兼顾信号丰富性与可靠性。

5. **R³ 整合设计精良**：胜者为基座、败者按证据筛选补充，再主动消除冗余（如用确定性机制替代纯提示建议），有效防止提示词随轮数膨胀。

6. **实验设计体现泛化意识**：50/450 划分、跨模型冻结评估、保留集上差距扩大等设计都指向泛化能力的真实检验，而非仅追求分数。

- **主动反馈流程复杂**：四阶段反馈管线（盲报、事后、调和、接地路由）涉及多轮模型调用，在更大规模任务上的成本效益比未论证。

### 8.4 应用限制

- **适用性未知**：对于非软件工程领域（如网页操作、数据库交互）的智能体，harness 组件的划分方式（结构 vs. 引导）是否依然成立未经验证；
- **基础模型快速迭代的适配成本**：虽然跨模型迁移实验证明了一定通用性，但最优 harness 仍为模型特定的，实际部署中可能需要周期性重新演化。
