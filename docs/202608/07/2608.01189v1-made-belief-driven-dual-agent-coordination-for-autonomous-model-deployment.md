## 摘要
基于大型语言模型的智能体现已具备强大的通用能力。然而，它们在处理特定领域任务时仍存在困难，这促使人们集成外部工具以扩展其能力。开源社区提供了大量AI模型，通常以异构研究工件的形式发布，而将它们转化为可调用的API代价高昂且劳动密集。因此，自动化模型部署对于弥合模型资源与工具可用性之间的鸿沟至关重要，但这是一个长周期、多阶段的任务，尚未得到充分探索。为应对这一挑战，我们提出了模型自动部署引擎（MADE），一种双智能体协调系统。具体而言，给定一个模型资源，MADE迭代地构建并验证部署工件，基于执行反馈更新其部署信念，并重新检查无效的上游工件，直到模型成功作为可调用API提供服务，供其他智能体使用。我们进一步引入了M2ABench，一个用于将模型转化为可调用API任务的基准。M2ABench包含122个真实世界模型，并配有标准化测试用例以供评估。实验结果表明，MADE实现了68.85%的部署成功率，分别比SWE-agent和OpenHands高出13.93和44.26个百分点。我们的代码和数据集公开在https://github.com/HITDiSC/MADE。

## Abstract
LLM-based agents now have strong general capabilities. However, they still struggle with domain-specific tasks, motivating the integration of external tools to broaden their capabilities. The open-source community offers a vast array of AI models typically released as heterogeneous research artifacts, whereas transforming them into ready-to-call APIs is costly and labor-intensive. Automated model deployment is therefore essential for bridging the gap between model resources and tool usability, yet it remains a long-horizon, multi-stage task that has not been sufficiently explored. To tackle this challenge, we introduce Model Automated Deployment Engine (MADE), a dual-agent coordination system. Specifically, given a model resource, MADE iteratively constructs and validates the deployment artifacts, updates its deployment belief based on execution feedback, and revisits invalid upstream artifacts until the model is successfully served as a ready-to-call API that can then be used by other agents. We further introduce M2ABench, a benchmark for the task of transforming Models to ready-to-call APIs. M2ABench comprises 122 real-world models with standardized test cases for evaluation. Experimental results demonstrate that MADE achieves a deployment success rate of 68.85%, outperforming SWE-agent and OpenHands by 13.93 and 44.26 percentage points, respectively. Our code and dataset are publicly available at https://github.com/HITDiSC/MADE.

- **研究背景**：LLM（大语言模型）智能体虽然通用能力强大，但在特定领域任务上表现不足，需要借助外部工具来扩展能力。开源社区提供了大量AI模型，但它们通常以异构的"研究工件"形式发布（包含代码、权重、配置文件、文档等），需要经过人工部署转化为可调用的API才能被LLM智能体使用。
- **核心问题**：将异构模型资源转化为"开箱即用"的API是一项**长周期、多阶段、高成本**的任务，存在两大核心挑战：
  1. **失败传播的延迟性**：部署失败往往表现在远离真正病因的下游环节——下游报错处不一定是要修复的地方，而正确的修复点可能在上游工件中。
  2. **全局视图与执行证据的矛盾**：驾驭长周期部署既需要轻量且实时的全局状态视图，又需要具体行动建立在第一手执行证据之上，而这两者在单一决策上下文内难以兼得。
- **论文意义**：首次系统性地将"自动化模型部署"作为独立任务提出，并为其构建了标准化基准（M2ABench），为LLM智能体调用多样化专业模型能力提供了基础设施。

## 2. 论文提出的方法论

### 2.1 总体框架：MADE 双智能体系统
- MADE（Model Automated Deployment Engine）是一个由**双智能体**协调的系统：
  - **Phase Manager（PM，阶段管理器）**：负责全局视角，跟踪全局部署状态，决定下一阶段应执行什么操作。
  - **Execution Master（EM，执行主控）**：负责局部视角，与代码和运行环境交互，收集第一手执行证据，执行具体操作。
- 两个智能体通过**共享工件存储**和**显式信念（belief）**进行协调，形成闭环。

### 2.2 部署管线（五阶段）
| 阶段 | 功能 | 输出 |
|---|---|---|
| **RepoIngest** | 解析模型资源，识别任务类型 | 结构化资源 |
| **DockerSetup** | 构建容器化执行环境（执行引导的纠错循环） | 运行中的容器 E |
| **WeightResolve** | 定位并获取模型检查点 | 本地可用的检查点 WR |
| **APIAdaptation** | 从模型推理代码重构推理过程，生成API及其I/O契约 | fD、(σin, σout) 服务代码与契约 |
| **APIValidation** | 启动服务、验证端点、修复失败 | 可调用的API A |

### 2.3 三个关键机制
- **工件状态信念（Artifact-State Belief）**：对每个跨阶段工件记录三类状态——absent（未产生）、present（存在且未被废止）、invalidated（被证明不可用）。信念自动维护，不消耗LLM调用。
- **向上证据：非单调废止（Non-Monotonic Invalidation）**：后置阶段的失败可回溯废止前置工件，通过维护废止集合 I，更新信念（如 present→invalidated），并使用保守关键词规则+PM确认来避免无效回溯。
- **向下控制：一致性门控监督（Consistency-Gated Supervision）**：仅在EM提议的操作与信念冲突或进度停滞时，PM才介入干预。门控触发是确定性的，只有触发后才调用一次LLM生成纠正指令（见公式6）。
- **冲突仲裁：基于证据的覆写（Evidence-Grounded Override）**：EM可对PM指令回应 accept / negotiate / reject，若PM指令基于过时信念，EM可用第一手执行证据覆写之。

### 2.4 推理闭包导航（Navigation to an Inference Closure）
- MADE不按相关性对仓库文件排序，而是识别**推理闭包 C†**（推理入口点 + 其传递导入的所有本地仓库文件）。
- 仅将唯一的语义决策交给一次LLM调用（基于 __main__ 守卫、AST检测的检查点加载调用、README引用等证据选择入口点），随后用确定性的递归静态导入解析构建完整闭包，无需额外LLM调用。

## 3. 实验设计

### 3.1 基准：M2ABench
- **首创性**：第一个"将模型转化为API"任务的基准。
- **规模**：包含 **122个**来自真实世界的开源模型，覆盖**五种模态**：

- **成功定义**：端点输出须符合声明的契约、匹配模型输出结构，并使用模型自身的检查点和推理逻辑。预测精度被明确排除（那是评估模型本身而非部署）。评价指标：**DSR（部署成功率）**、LLM调用次数、Token消耗量。

## 6. 论文的主要结论与发现

- **主结果**：MADE 在 M2ABench 上达到 68.85% 的 DSR（成功部署84/122个模型），超过 SWE-agent（54.92%）**13.93个百分点**，超过 OpenHands（24.59%）**44.26个百分点**。表明**部署专用工作流**比直接套用通用软件工程智能体更可靠。
- **效率权衡**：MADE平均每次成功消耗 1058.297k tokens，比 SWE-agent 节省 68.68% 的token消耗且DSR更高；虽然 OpenHands 消耗更少 tokens（846.117k）但DSR远低（24.59%），表明低token消耗不一定能带来可靠部署。
- **调用模式**：MADE单次成功部署的LLM调用次数最多，但单次调用的上下文平均比两个基线小得多——验证了其设计哲学：将部署分解为频繁、范围受限的决策，辅以确定性导航和验证，而非少数昂贵的长时间上下文交互。
- **Token分布**：token消耗集中在**APIValidation和APIAdaptation**两阶段（尤其是APIValidation占比最大且随总消耗增加），说明高成本部署主要由反复的"执行—失败—诊断—修复—重新验证"循环驱动；长尾分布（少数困难仓库消耗极高成本）。
- **消融发现**：
  - 去掉双智能体协调 → DSR 从 68.85% 跌至 27.87%（-40.98pp），成功部署数从84降至34。
  - 去掉推理闭包导航 → DSR 跌至 16.39%（-52.46pp），成功部署数仅剩20，影响最大。
- **失败根因**：38个失败案例中，**50% 因模型权重缺失或无法获取**（WeightResolve阶段即终止），是最常见瓶颈；其余主要集中为导入解析失败（13.16%）、Docker构建失败（10.53%）、服务启动失败（10.53%）、契约不匹配（10.53%）和CUDA运行时失败（5.26%）。

## 7. 优点

- **问题定义清晰且有价值**：首次将"模型资源→可调用API"定义为独立研究任务，填补了LLM工具生态中"最后一公里"的空白。
- **方法论设计精巧**：
  - **双智能体分离关注点**：全局协调（PM）与局部执行（EM）分工明确，避免任一单一视角的盲区。
  - **信念机制的"轻量性"**：信念计算与门控决策是确定性的（无需LLM调用），LLM监督仅在冲突或停滞时被触发，成本与信号数量成正比而非与轨迹长度成正比——这是一项优雅的成本控制设计。
  - **非单调废止 + 证据覆写**：允许执行证据回溯修正全局判断，可有效处理"失败在下游、根因在上游"的长程传播问题。
  - **推理闭包导航将不确定性最小化**：将整个仓库导航中唯一的语义决策压缩到单次LLM调用，其余全部由静态分析确定性地完成，系统性地降低了token消耗与错误积累。
  - **执行引导的环境纠错与推理-契约共同生成**：强调"忠实度"（faithfulness）——强制从模型自身代码重构推理过程，而非用替代品。
- **评估严谨**：评估器与基线隔离、基于端到端契约符合性的成功定义（不含预测准确率）、人工撰写测试用例、人工检查所有资源齐备性，这些都增强了基准的可靠性。
- **开源**：代码和数据集公开，支持社区复现与扩展。
- **实验分析深入**：不仅报DSR，还分析了token分布、阶段占比、失败根因，为后续改进提供方向指引。

## 8. 不足与局限

- **模型资源可用性瓶颈未被解决**：半数以上的失败源于检查点无法解析/获取（WeightResolve阶段），这本质上是外部资源依赖问题，而非部署系统逻辑问题。但此比例限制了管线后续阶段在失败样本上的验证深度——剩余环节能否在这些样本上成功尚不可知。
- **算力成本信息不完整**：未报告每次部署的墙钟时间或GPU利用率，也未给出GPT-5.2调用的精确费用计算，实际落地的成本模型不够透明。
- **泛化性有限**：
  - 仅使用 GPT-5.2 一个骨干LLM，未验证MADE在开源模型（如 Llama 系列）或其他闭源模型上的稳定性。

- **场景限制**：任务范围明确排除了训练、微调、批处理、流式处理和生成级优化；未考虑多GPU并行推理、模型分片、生产级部署等现实工程场景。
