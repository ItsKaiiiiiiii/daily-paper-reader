## 摘要
基于大语言模型的智能体如今具备强大的通用能力。然而，它们在领域特定任务上仍表现不佳，这促使集成外部工具以拓展其能力。开源社区提供了大量通常以异构研究工件形式发布的AI模型，而将它们转化为可直接调用的API成本高昂且劳动密集。因此，自动化模型部署对于弥合模型资源与工具可用性之间的差距至关重要，但它仍然是一项长期、多阶段且尚未充分探索的任务。为应对这一挑战，我们提出了模型自动部署引擎（MADE），一个双智能体协同系统。具体而言，给定一个模型资源，MADE迭代地构建并验证部署工件，基于执行反馈更新其部署信念，并重新审视无效的上游工件，直到模型成功作为可供其他智能体使用的可直接调用API提供服务。我们进一步介绍了M2ABench，一个面向将模型转换为可直接调用API的任务的基准。M2ABench包含122个真实世界的模型以及用于评估的标准化测试用例。实验结果表明，MADE实现了68.85%的部署成功率，分别比SWE-agent和OpenHands高出13.93和44.26个百分点。我们的代码和数据集可在https://github.com/HITDiSC/MADE公开获取。

## Abstract
LLM-based agents now have strong general capabilities. However, they still struggle with domain-specific tasks, motivating the integration of external tools to broaden their capabilities. The open-source community offers a vast array of AI models typically released as heterogeneous research artifacts, whereas transforming them into ready-to-call APIs is costly and labor-intensive. Automated model deployment is therefore essential for bridging the gap between model resources and tool usability, yet it remains a long-horizon, multi-stage task that has not been sufficiently explored. To tackle this challenge, we introduce Model Automated Deployment Engine (MADE), a dual-agent coordination system. Specifically, given a model resource, MADE iteratively constructs and validates the deployment artifacts, updates its deployment belief based on execution feedback, and revisits invalid upstream artifacts until the model is successfully served as a ready-to-call API that can then be used by other agents. We further introduce M2ABench, a benchmark for the task of transforming Models to ready-to-call APIs. M2ABench comprises 122 real-world models with standardized test cases for evaluation. Experimental results demonstrate that MADE achieves a deployment success rate of 68.85%, outperforming SWE-agent and OpenHands by 13.93 and 44.26 percentage points, respectively. Our code and dataset are publicly available at https://github.com/HITDiSC/MADE.

### 1. 论文的核心问题与整体含义

  - **延迟故障传播**：部署失败常常源于上游工件，但错误在下游才显现，导致智能体反复修补症状而非根因；
  - **全局状态维护难**：长周期部署中，维持全局视图与第一手执行证据之间的平衡极为困难；
  - **现有通用编码智能体（如SWE-agent、OpenHands）采用广泛试错策略，token开销大且部署成功率有限**。
- **整体含义**：本文首次系统定义了"自动化模型部署"这一任务，并提供了基准（M2ABench）与可行方案（MADE），为LLM调用多样化专用模型能力奠定基础设施。

### 2. 论文提出的方法论

#### 2.1 核心思想
MADE 提出**信念驱动的双智能体协调**机制：用一个轻量、确定、可修正的"部署信念"（belief）来记录各部署工件（artifact）的状态，用"状态变化"而非反复的LLM检查来驱动长周期部署协调。

#### 2.2 任务形式化定义
给定模型资源 R 和部署主机 H，需构建部署工件集合：

**D = {E, Wᵣ, f_D, σ_in, σ_out, A}**

| 符号 | 含义 |
|---|---|
| E | 模型代码运行的执行环境 |
| Wᵣ | 模型检查点（权重） |
| f_D | 单实例推理过程（含预处理、模型执行、后处理） |
| (σ_in, σ_out) | 显式、机器可读的输入/输出契约 |
| A | 对外提供的可调用API服务 |

#### 2.3 部署管线（5阶段）
1. **RepoIngest**：解析模型资源，识别仓库布局与任务类型；
2. **DockerSetup**（与WeightResolve并行）：基于声明依赖+代码推断依赖构建容器化环境，通过**执行引导式纠错循环**（构建/执行失败反馈→修正环境配置）适配GPU等硬件配置；
3. **WeightResolve**：仅从模型指定来源定位并检索检查点；
4. **APIAdaptation**：从模型自身推理代码重构 f_D（不手写能力），采用**推理-契约协同生成**，同时生成预处理/后处理逻辑与其I/O契约，并校验契约字段与代码访问字段的一致性；
5. **APIValidation**：启动服务、健康检查、调用M2ABench评估器测试线上端点；小问题就地修复，指示上游工件缺陷的严重失败上报至协调层。

#### 2.4 双智能体协调机制
- **Execution Master (EM)**：阶段内执行者，负责选择工具、收集第一手代码与运行时证据；
- **Phase Manager (PM)**：跨阶段管理者，决定下一阶段运行及输出有效性判断。

**核心机制包括三个部分：**

**(a) 工件状态信念（Artifact-state Belief）**：每个跨阶段工件 a ∈ A 的状态 ˆZ[a] 三态取值：
- `absent`：尚未产生
- `present`：存在且未被失效
- `invalidated`：后续执行证据证明其不可用

信念维护全程**无LLM调用，纯确定性自动更新**。

**(b) 向上证据：非单调失效（Non-monotonic Invalidation）**：当后阶段失败提供针对先前工件的证据时，更新失效集合：

**I(t+1) = I(t) ∪ R(o_t)**（R(o_t) 为候选根因工件集合）

然后信念被重算，将相关工件从 `present` 改为 `invalidated`。R 只考虑先前执行阶段的工件、采用保守关键字规则并需PM确认。

**(c) 向下控制：一致性门控监督（Consistency-gated Supervision）**：仅在EM的提议动作与信念冲突或出现停滞时介入：

**Intervene(u_t, h_t; ˆZ) = 1** 当且仅当以下任一成立：
- ∃ a ∈ Out(u_t)：ˆZ[a] = present（输出已被认定为present，即组件重复产出）
- ∃ a ∈ In(u_t)：ˆZ[a] ≠ present（输入不可用）
- h_t 指示进展停滞（同一工具使用k次无新工件、或连续m轮出错）

门控触发是**确定性**的；触发后PM才进行**一次**LLM调用来生成纠正指令。

**(d) 冲突仲裁**：EM可回应 `accept / negotiate / reject` PM指令，挑战时附上本地证据，以第一手执行证据覆盖过时的全局信念。这形成一个闭环：**执行证据→更新信念→门控约束→PM纠偏→EM执行→新证据**。

#### 2.5 推理闭包导航（Navigation to an Inference Closure）
- 核心洞察：**文件选择错误模式不对称**——遗漏一个配置加载器或工具模块会导致整体重构失败，而纳入无关文件仅消耗上下文预算；
- 方法：不按相关性排序文件，而是确定**推理闭包 C†**（入口点+所有传递导入的本地文件）：
  - 仅有一次LLM调用做语义决策（入口点选择），利用确定性证据（`__main__` 守卫、AST检测的检查点加载调用、README中的引用）做辅助；
  - 入口点选定后，通过静态导入图递归解析本地依赖，**无需额外LLM调用**。

### 3. 实验设计

#### 3.1 数据集 / 基准
- **M2ABench**：首个面向"模型→可调用API"的基准，包含 **122个真实世界开源模型**，覆盖5大模态：
  - 文本 49个（40.16%）
  - 图像 27个（22.13%）
  - 科学结构（蛋白质、分子、生理信号）25个（20.49%）
  - 音频 13个（10.66%）
  - 多模态 8个（6.56%）
- 每个模型配备 **5个**人工编写的测试用例，输入/输出来自模型的文档示例或训练数据样本，输出统一以文本形式表示。模型均按其原始形式使用，不修改代码或文档。

#### 3.2 评估指标
- **成功定义**：端点对所有测试输入产生**结构一致**的输出（类型、嵌套、格式匹配）；不评估预测准确率（那是模型本身的能力，而非部署正确性）；
- **DSR（部署成功率）**：只有当全部5个测试用例的输出结构均匹配时才计为成功；
- **LLM调用次数**：每次成功部署的LLM调用数；
- **Token消耗**：每次成功部署的总token数。

### 6. 主要结论

1. **MADE显著优于通用编码智能体**：DSR 68.85%，比SWE-agent高13.93个百分点、比OpenHands高44.26个百分点；
2. **效率与效果的平衡**：MADE 比SWE-agent节省68.68%的token（1058k vs 3379k）且DSR更高；虽然比OpenHands消耗更多token，但DSR优势巨大；
3. **LM调用模式差异**：MADE调用频次高但每次上下文更小，反映其"频繁、范围受限的决策 + 确定性导航/验证"的设计理念；
4. **Token集中阶段**：APIValidation 和 APIAdaptation 占token消耗大头，高成本部署主要由反复执行-失败-修复-再验证循环驱动；
5. **消融结论**：双智能体协调和推理闭包导航都至关重要，后者（-52.46pp）影响更甚；
6. **主要失败瓶颈**：检查点解析失败占所有失败案例的50%，说明模型资源可用性是当前管道的最大瓶颈。

### 7. 优点

- **任务定义清晰**：首次形式化定义了"模型资源→API"的部署任务（D的5元组）及端到端成功标准；
- **机制设计精巧**：
  - 信念维护与门控计算**均为确定性操作**（不消耗LLM调用），LLM监督只在门控触发后介入，成本控制合理；
  - 非单调信念更新解决了"延迟失败传播"这一长周期任务的核心痛点；
  - EM有权限挑战PM（negotiate/reject），避免全局信念滞后于实际执行状态；
- **推理闭包导航设计合理**：利用静态导入图确定闭包，免去大量LLM调用做相关性排序，且在消融中证明价值巨大；
- **基准构建规范**：122个真实模型、人工测试用例、统一文本化输出对比、评估器隔离防止作弊；
- **成本分析细致**：提供了阶段级token分解，揭示瓶颈所在；
- **失败分析到位**：对全部失败案例进行人工根因分类，不回避问题。

### 8. 不足与局限

- **骨干模型单一**：所有实验仅用GPT-5.2，未评估MADE在其他LLM（开源模型、小模型）上的表现，泛化性存疑；
- **领域范围限制**：只部署研究型模型，且明确排除训练、微调、批处理、流式处理、生产级服务优化，实际生产场景的部署需求更复杂；
- **成功标准较保守**：仅要求结构一致性，不考核输出质量，一个部署了错误但结构正确的模型仍会被计为"成功"；
- **欠缺统计稳健性**：未报告多次运行的标准差或置信区间，DSR差异的显著性未知；
- **检查点依赖**：50%的失败源于权重不可获取，但权重获取策略未作为消融变量单独研究；
- **上下文预算问题**：虽然闭包比通用检查好，但对于依赖大量可视化库或动态导入的仓库，静态导入解析可能遗漏必要文件；
- **成本未完全透明**：未报告GPU总使用时长、能耗等计算资源成本，仅报告token数；
- **未来方向**：论文未讨论如何将MADE扩展到多模型并发部署、模型更新/版本切换等持续部署场景。
